Uma competência reúne instruções, recursos e scripts opcionais para que o Enconvo possa seguir um fluxo de trabalho de forma fiável. Crie uma quando se vir a explicar sempre o mesmo procedimento, como rever código ou formatar notas de reunião. Pode partilhar competências com a sua equipa ou com a comunidade.

<Note>
As competências utilizam a **divulgação progressiva** para gerir o contexto com eficiência: o Enconvo começa com os metadados de cada competência (nome, descrição, caminho do ficheiro). As instruções completas só são carregadas quando uma competência é ativada.
</Note>

## Gerir as suas competências

Abra **Definições → Competências**. Todos os Agentes partilham estas competências, e cada Agente pode adicionar as suas nas respetivas definições.

- Os cartões no topo contam **Todas as competências**, as que estão **Ativadas, nunca usadas**, as que estão **Em mais de uma pasta** e as que estão **Desativado**. Clique num cartão para listar apenas essas.
- Cada linha mostra **Onde está** (integrada, ou a pasta ou app de onde vem) e quando foi o **Último uso**. Desative as competências de que os seus Agentes não precisam com o interruptor no fim da linha, ou selecione várias e desative-as em conjunto.
- **Adicionar a partir do GitHub** instala uma competência a partir de um repositório, e **Importar** adiciona uma a partir de uma pasta no seu Mac. Consulte [Instalar competências](#instalar-competências).
- **Os seus skills** lista as competências que criou, por origem: **Gravado**, **Aprendido**, **Script**, **Escrita** ou **Instalado**. Clique numa para ver os respetivos **Passos**, **Cuidados** e **Histórico**. Consulte [Competências com passos guardados](#competências-com-passos-guardados).

Na Janela de chat, pode também abrir as Competências diretamente na janela a partir de **Plugins** na barra de ícones.

## Como é uma competência

Uma competência é uma pasta com um ficheiro `SKILL.md`, mais scripts e referências opcionais.

```
my-skill/
├── SKILL.md          # Required: instructions + metadata
├── scripts/          # Optional: executable code
├── references/       # Optional: documentation
└── assets/           # Optional: templates, resources
```

### Formato do SKILL.md

O `SKILL.md` tem de começar com um bloco de frontmatter que tenha um `name` e uma `description`:

```markdown
---
name: my-skill
description: Explain exactly when this skill should and should not trigger.
---

Step-by-step instructions for EnConvo to follow.
```

<Tip>
O Enconvo escolhe uma competência pela respetiva `description`, por isso dê-lhe um âmbito e limites claros. Diga **quando** utilizar a competência e **quando não** utilizar.
</Tip>

## Utilizar uma competência

Pode chamar uma competência pelo nome, ou deixar o Enconvo escolher uma que corresponda ao seu pedido.

### Chamar uma competência pelo nome

Escreva `/` seguido do nome da competência na SmartBar ou na conversa:

```
/code-reviewer Review this function for security issues
/meeting-notes Format these raw notes into a structured summary
/api-checker Check the health of api.example.com
```

Esta é a forma mais fiável: obtém exatamente a competência que quer. Para listar apenas competências, escreva `$`.

As competências dos plugins que instalou estão também nos menus `/` e `$`, com o nome `plugin:skill` como no Claude Code.

### Deixar o Enconvo escolher

Quando não nomeia uma competência, o Enconvo faz corresponder o seu pedido à competência mais relevante pela respetiva `description`:

1. Escreve: "Resume estas notas de reunião em tarefas a realizar"
2. O Enconvo analisa todas as descrições de competências disponíveis
3. A competência `meeting-notes` corresponde ("...formatar transcrições de reuniões em bruto em notas estruturadas com tarefas a realizar...")
4. A competência é ativada e as respetivas instruções orientam a resposta

A correspondência faz-se pelo significado, e não apenas por palavras-chave partilhadas, pelo que um pedido formulado de outra forma que não a descrição, ou escrito noutra língua, encontra na mesma a competência. Para garantir que um Agente vê sempre uma competência, fixe-a nas definições **Ferramentas e competências** do Agente; consulte [Agentes](/pt/ai/agents).

### Escrever descrições que correspondam bem

Uma boa correspondência depende de uma `description` bem escrita:

| Qualidade | Exemplo |
|---------|---------|
| **Demasiado vaga** | "Ajuda com código" |
| **Demasiado ampla** | "Faz tudo o que esteja relacionado com programação" |
| **Boa** | "Revê código à procura de erros, problemas de segurança e boas práticas. Utilizar quando o utilizador pede uma revisão de código ou quer melhorar a qualidade do código. Não utilizar para geração de código nem para escrever código novo." |

Uma boa descrição tem três partes:

- **O que faz**: "Revê código à procura de erros, problemas de segurança e boas práticas"
- **Quando acionar**: "Utilizar quando o utilizador pede uma revisão de código"
- **Quando não acionar**: "Não utilizar para geração de código nem para escrever código novo"

## Onde vivem as competências

O Enconvo lê competências a partir de vários locais, cada um com o seu âmbito:

| Âmbito | Localização | Utilize para |
|-------|----------|------------|
| **Projeto** | `$PROJECT/.agents/skills/` (também `.enconvo/skills/`, `.claude/skills/` e `.codex/skills/`) | Competências para um projeto ou espaço de trabalho |
| **Utilizador** | `~/.agents/skills/` (também `~/.enconvo/skills/`, `~/.claude/skills/` e `~/.codex/skills/`) | Competências pessoais para todos os seus projetos |
| **Sistema** | Incluídas no Enconvo | Competências integradas disponíveis para todos |

Cada Agente pode também ter as suas próprias competências: adicione-as em **Competências** nas definições do Agente.

Se duas competências em locais diferentes partilharem um nome, ambas ficam disponíveis; o Enconvo não as junta. **Definições → Competências** lista estas competências em **Em mais de uma pasta**.

### Competências de projeto

As competências de projeto vivem dentro da pasta do seu projeto e só estão disponíveis quando esse projeto está ativo:

```
my-project/
├── .agents/
│   └── skills/
│       ├── deploy-checklist/
│       │   └── SKILL.md
│       └── pr-template/
│           └── SKILL.md
├── src/
└── package.json
```

Utilize-as para competências que dependem das convenções, da estrutura de ficheiros ou das ferramentas de um projeto.

### Competências de utilizador

As competências de utilizador em `~/.agents/skills/` estão disponíveis em todos os projetos. Utilize-as para competências pessoais que não pertencem a um só projeto:

```
~/.agents/skills/
├── email-composer/
│   └── SKILL.md
├── meeting-notes/
│   └── SKILL.md
└── code-reviewer/
    └── SKILL.md
```

## Criar uma competência

### Com o criador de competências

A forma mais rápida de criar uma competência é o criador integrado:

```
/skill-creator
```

O criador guia-o por:

1. O que a competência faz
2. Quando deve ser acionada
3. Se deve ser só de instruções ou incluir scripts

Só instruções é a predefinição e a abordagem recomendada. Adicione scripts apenas quando precisar de comportamento determinístico ou de ferramentas externas.

### À mão

Crie uma pasta com um ficheiro `SKILL.md`:

<Steps>
  <Step title="Criar a pasta da competência">
    ```bash
    mkdir -p ~/.agents/skills/my-skill
    ```
  </Step>
  <Step title="Escrever o SKILL.md">
    ```bash
    cat > ~/.agents/skills/my-skill/SKILL.md << 'EOF'
    ---
    name: my-skill
    description: Summarize selected text into bullet points. Use when the user asks for a summary or key takeaways. Do not use for translation or rewriting tasks.
    ---

    ## Instructions

    1. Read the selected text from the user's input.
    2. Identify the 3-5 most important points.
    3. Return a bullet-point summary.
    4. Keep each bullet under 20 words.
    EOF
    ```
  </Step>
  <Step title="Verificar que aparece">
    O Enconvo deteta automaticamente as alterações às competências. Se a nova competência não aparecer, reinicie o Enconvo.
  </Step>
</Steps>

### Escrever as instruções

O corpo do `SKILL.md`, abaixo do frontmatter, contém as instruções que a IA segue. Escreva-as como passos claros e no imperativo:

````markdown
---
name: changelog-generator
description: Generate a changelog from git commits. Use when the user asks to create a changelog, release notes, or commit summary. Do not use for general git operations.
---

## Instructions

1. Read the git log for the specified date range or number of commits.
2. Group commits by category:
   - **Features**: New functionality (commits starting with "feat:")
   - **Fixes**: Bug fixes (commits starting with "fix:")
   - **Breaking Changes**: Changes that break backward compatibility
   - **Other**: Everything else
3. For each commit, write a user-facing description (not the raw commit message).
4. Format as markdown with version header, date, and categorized bullet points.
5. Highlight breaking changes with a warning callout.

## Output Format

```
## v1.2.0 (2024-01-15)

### Features
- Added dark mode support for all pages
- New export to PDF option in reports

### Fixes
- Fixed login timeout on slow connections
- Resolved duplicate notification issue

### Breaking Changes
⚠️ API endpoint `/v1/users` now requires authentication
```
````

### Dicas para boas competências

- **Mantenha cada competência focada.** Uma competência faz uma só tarefa. Uma competência que faz demasiadas coisas é mais difícil de acionar corretamente e de manter. Se estiver a escrever 10 ou mais passos que abrangem várias tarefas, divida-a em competências separadas.
- **Seja específico quanto às entradas.** Diga exatamente de onde vem a entrada: "Ler o texto selecionado", "Analisar o ficheiro anexado", "Utilizar o URL da mensagem do utilizador".
- **Defina o formato de saída.** Inclua um exemplo concreto do aspeto que a saída deve ter, para que os resultados se mantenham consistentes.
- **Trate os casos limite.** Adicione instruções para os casos limite mais comuns: "Se não forem encontrados commits, indicar que o intervalo está vazio" ou "Se a entrada não for JSON válido, pedir ao utilizador que verifique o formato".
- **Escreva passos no imperativo.** Seja explícito quanto às entradas, aos passos e às saídas esperadas. Instruções vagas levam a resultados inconsistentes.
- **Prefira instruções a scripts.** As instruções em linguagem corrente são mais fáceis de escrever, de depurar e de alterar. Utilize scripts apenas quando precisar de comportamento determinístico ou de ferramentas externas.
- **Utilize limites claros.** Na descrição, indique o que a competência deve tratar e o que não deve.
- **Teste as descrições de acionamento.** Experimente pedidos diferentes para confirmar que a competência é acionada, e não é acionada, quando deve.
- **Versione as suas competências.** Mantenha as competências partilhadas pela equipa em controlo de versões (git), para poder acompanhar alterações, reverter e colaborar.

## Adicionar scripts

Para competências que precisam de lógica executável, adicione uma pasta `scripts/`:

```
my-skill/
├── SKILL.md
└── scripts/
    └── fetch_data.sh
```

Refira os scripts no seu `SKILL.md`:

````markdown
---
name: api-checker
description: Check API endpoint health and response times.
---

## Instructions

1. Run the health check script:
   ```bash
   bash scripts/fetch_data.sh $URL
   ```
2. Parse the JSON output.
3. Report status, response time, and any errors.
````

### Quando utilizar scripts

| Utilize scripts quando | Utilize só instruções quando |
|-----------------|---------------------------|
| Precisa de saída determinística (formatos exatos, cálculos) | A tarefa é sobretudo de raciocínio e linguagem |
| Interage com APIs externas ou bases de dados | A tarefa utiliza apenas as capacidades integradas da IA |
| Precisa de processar ou transformar dados por programação | A tarefa consiste em escrever, resumir ou analisar |
| Precisa de autenticação ou de tratamento de credenciais | As instruções por si só são suficientes |

## Adicionar referências

Inclua ficheiros de documentação ou de contexto que a competência possa consultar:

```
my-skill/
├── SKILL.md
├── references/
│   ├── api-docs.md
│   └── examples.md
└── scripts/
    └── run.sh
```

Refira-os nas instruções:

```markdown
Consult `references/api-docs.md` for the API schema before making requests.
```

As referências são úteis para:

- Documentação de API que a competência precisa de seguir
- Guias de estilo ou diretrizes de marca
- Exemplos de código e modelos
- Conhecimento específico de um domínio

## Instalar competências

Utilize `/skill-installer` para instalar uma competência a partir da loja de competências do Enconvo ou do GitHub. Também pode instalar a partir do Skills.sh, do ClawHub e de URLs ZIP diretos.

### A partir da loja de competências do Enconvo

Procure uma competência pelo nome e instale-a:

```
/skill-installer pdf
```

Isto pesquisa a loja de competências do Enconvo e instala a competência correspondente. O Enconvo deteta automaticamente as competências acabadas de instalar.

### A partir do GitHub

Instale uma competência diretamente a partir do URL de um repositório do GitHub:

```
/skill-installer https://github.com/anthropics/skills/tree/main/skills/pptx
```

O URL pode apontar para uma subpasta, pelo que pode instalar uma competência de um repositório maior sem clonar tudo.

### A partir de uma pasta no seu Mac

1. Abra **Definições → Competências** e clique em **Importar**.
2. Escolha uma pasta que contenha subpastas de competências, cada uma com um `SKILL.md`.

O Enconvo adiciona a pasta aos locais de onde lê competências, e as respetivas competências são partilhadas por todos os Agentes. Para deixar de utilizar a pasta, escolha-a no menu de origem e depois **Remover pasta**. A própria pasta permanece no disco.

## Competências com passos guardados

Cada Fluxo de trabalho guardado é também uma competência com o seu próprio `SKILL.md`, e uma competência pode guardar os passos de uma tarefa que já realizou. Quando executa uma competência assim, os respetivos passos guardados são executados primeiro, sem o modelo principal, o que é mais rápido e mais barato. Um passo que já não se adequa, como um botão que mudou de sítio, é reparado a partir das notas e das capturas de ecrã da própria competência. Só quando isso falha é que um Agente faz a tarefa a partir do `SKILL.md`.

Em **Os seus skills**, uma competência marcada com **Executa primeiro os passos guardados** tem passos; uma marcada com **Só instruções** não tem. O **Histórico** de cada competência mostra como correram as respetivas execuções e o que aprendeu, e pode restaurar uma versão anterior.

### Transformar uma gravação numa competência

Pode transformar a gravação de uma tarefa que realizou numa competência. Cada ação gravada torna-se um passo verificado, e a respetiva captura de ecrã é guardada para reparações. A competência continua a ser um **Rascunho** até uma execução sua funcionar.

### Executar um script como passo

Uma competência pode guardar um script do [Code Mode](/pt/configuration/code-mode) na sua própria pasta `scripts` e executá-lo como um dos seus passos, para que uma tarefa que faz muitas chamadas de ferramentas seja executada como um só passo.

## Deixar as competências aprenderem como trabalha

As competências podem aprender como gosta que as tarefas sejam feitas, tal como as Memórias aprendem factos. Abra **Definições → Memória** e ative **Aprender como fazer**:

- Quando corrige a forma como uma tarefa foi feita, ou um passo teve de ser reparado, a competência aprende-o de imediato. A conversa mostra uma nota **Aprendido** com **Anular**.
- Quando uma tarefa surge pela segunda vez, torna-se uma nova competência.
- A Revisão de Memória e a Arrumação de Memória tratam também das competências.

Em **Ao alterar passos**, escolha **Usar já**, ou **Perguntar-me primeiro** para que uma alteração aos passos de uma competência aguarde que clique em **Aplicar** na respetiva nota. Os Cuidados entram de imediato em qualquer dos casos. Pagamentos, envios e eliminações perguntam-lhe sempre primeiro, e as chaves e as palavras-passe nunca são aprendidas.

## Gerir competências

### Ver as suas competências

**Definições → Competências** lista as competências partilhadas por todos os Agentes. Escolha uma vista no topo:

| Vista | Mostra |
| --- | --- |
| **Todas as competências** | Cada competência uma só vez, mesmo quando várias pastas têm uma cópia |
| **Ativadas, nunca usadas** | Competências que são oferecidas aos Agentes em todas as conversas, mas que não utilizaram |
| **Em mais de uma pasta** | Competências com uma cópia em mais do que uma pasta, como para o Claude Code e o Codex |
| **Desativado** | Competências que os Agentes não recebem |

Pesquise, filtre por origem (**Todas as fontes**, **Integrado**, **De plugins** ou uma pasta) ou ordene por **Nome de A a Z** ou **Último uso**.

### Atualizar competências

- **Competências da loja**: execute `/skill-installer` novamente para verificar se há uma versão mais recente.
- **Competências do GitHub**: execute novamente o instalador com o mesmo URL.
- **As suas próprias competências**: edite diretamente o ficheiro `SKILL.md`. O Enconvo deteta a alteração automaticamente.

### Desativar uma competência

Pode desativar uma competência sem a eliminar:

1. Abra **Definições → Competências**.
2. Encontre a competência.
3. Desligue o respetivo interruptor.

Os Agentes não podem utilizar uma competência desativada, pelo nome nem por correspondência, até a voltar a ativar. Um perfil de app que fixe a competência pode continuar a utilizá-la.

## Exemplos de competências

### Revisor de código

```markdown
---
name: code-reviewer
description: Review code for bugs, security issues, and best practices. Use when the user asks for a code review or wants to improve code quality. Do not use for code generation or writing new code.
---

## Instructions

1. Read the provided code carefully.
2. Check for:
   - Logic errors and edge cases
   - Security vulnerabilities (injection, XSS, etc.)
   - Performance issues
   - Code style and readability
3. Provide feedback as a numbered list.
4. For each issue, include:
   - Severity (Critical / Warning / Suggestion)
   - Line reference
   - Explanation and fix
```

### Notas de reunião

```markdown
---
name: meeting-notes
description: Format raw meeting transcripts into structured notes with action items. Use when the user provides meeting notes, transcripts, or asks to organize meeting content. Do not use for scheduling or calendar tasks.
---

## Instructions

1. Parse the meeting transcript or raw notes.
2. Extract and organize into sections:
   - **Attendees**: List all participants
   - **Key Decisions**: Bullet-point decisions made
   - **Discussion Summary**: 3-5 sentence overview
   - **Action Items**: Table with Owner, Task, Deadline
3. Use markdown formatting for readability.
```

### Mensagem de commit do git

````markdown
---
name: commit-message
description: Generate conventional commit messages from staged changes. Use when the user asks for a commit message or wants to commit changes. Do not use for general git operations like branching or merging.
---

## Instructions

1. Read the staged diff (use `git diff --staged`).
2. Identify the type of change:
   - feat: New feature
   - fix: Bug fix
   - docs: Documentation
   - refactor: Code restructuring
   - test: Adding tests
   - chore: Maintenance
3. Write a commit message following Conventional Commits format:
   ```
   type(scope): concise description

   - Detail 1
   - Detail 2
   ```
4. Keep the subject line under 72 characters.
5. Include a body only if the change needs explanation.
````

### Gerador de documentação de API

````markdown
---
name: api-docs
description: Generate API documentation from source code. Use when the user asks to document an API, endpoint, or function. Do not use for general code documentation or README files.
---

## Instructions

1. Read the source code file(s) provided.
2. For each endpoint or public function, document:
   - **Method & Path** (for HTTP) or **Signature** (for functions)
   - **Description**: What it does in one sentence
   - **Parameters**: Name, type, required/optional, description
   - **Response**: Structure and example
   - **Errors**: Possible error codes and meanings
3. Format as markdown with code examples.
4. Include a curl example for each HTTP endpoint.

## Output Format

### `POST /api/users`

Create a new user account.

**Parameters:**

| Name | Type | Required | Description |
|------|------|----------|-------------|
| email | string | Yes | User's email address |
| name | string | Yes | Display name |

**Response (201):**
```json
{ "id": "usr_123", "email": "user@example.com", "name": "John" }
```
````
