Навичка об’єднує інструкції, ресурси й необов’язкові скрипти, щоб Enconvo міг надійно виконувати робочий процес. Створіть її, коли вам доводиться раз за разом пояснювати одну й ту саму процедуру, наприклад як рецензувати код чи як оформлювати нотатки зустрічі. Навичками можна ділитися з командою або спільнотою.

<Note>
Навички використовують **поступове розкриття**, щоб ефективно керувати контекстом: Enconvo починає з метаданих кожної навички (назва, опис, шлях до файлу). Повні інструкції завантажуються лише тоді, коли навичку активовано.
</Note>

Це відео розповідає про Навички, потім про MCP-сервери, Плагіни та Магазин розширень.

## Керування навичками

Відкрийте **Параметри → Навички**. Ці навички спільні для всіх Агентів, а кожен Агент може додати власні у своїх параметрах.

- Картки вгорі підраховують **Усі навички**, ті, що **Увімкнено, ніколи не використовувалося**, ті, що **У кількох папках**, і ті, що **Вимкнено**. Натисніть картку, щоб показати лише їх.
- Кожен рядок показує **Де розташовано** (вбудована, або папка чи застосунок, звідки вона походить) і коли її було **Востаннє використано**. Вимикайте навички, які не потрібні вашим Агентам, перемикачем у кінці рядка або виберіть кілька й вимкніть їх разом.
- **Додати з GitHub** встановлює навичку з репозиторію, а **Імпортувати** додає її з папки на вашому Mac. Див. [Інсталювання навичок](#інсталювання-навичок).
- **Ваші навички** перелічує створені вами навички за походженням: **Записано**, **Засвоєно**, **Скрипт**, **Написаний** або **Інстальовано**. Натисніть одну, щоб побачити її **Кроки**, **Підводні камені** та **Історію**. Див. [Навички зі збереженими кроками](#навички-зі-збереженими-кроками).

У Вікні чату навички також можна відкрити прямо у вікні через **Плагіни** на панелі іконок.

## Як виглядає навичка

Навичка — це папка з файлом `SKILL.md`, а також необов’язковими скриптами та довідковими матеріалами.

```
my-skill/
├── SKILL.md          # Required: instructions + metadata
├── scripts/          # Optional: executable code
├── references/       # Optional: documentation
└── assets/           # Optional: templates, resources
```

### Формат SKILL.md

`SKILL.md` має починатися з блоку frontmatter, що містить `name` і `description`:

```markdown
---
name: my-skill
description: Explain exactly when this skill should and should not trigger.
---

Step-by-step instructions for EnConvo to follow.
```

<Tip>
Enconvo вибирає навичку за її `description`, тож задайте чіткі обсяг і межі. Вкажіть, **коли** використовувати навичку і **коли ні**.
</Tip>

## Використання навички

Навичку можна викликати за назвою або дозволити Enconvo вибрати ту, що відповідає вашому запиту.

### Виклик навички за назвою

Введіть `/` і назву навички в SmartBar або в чаті:

```
/code-reviewer Review this function for security issues
/meeting-notes Format these raw notes into a structured summary
/api-checker Check the health of api.example.com
```

Це найнадійніший спосіб: ви отримуєте саме ту навичку, яку хочете. Щоб показати лише навички, введіть `$`.

Навички встановлених вами плагінів також є в меню `/` і `$` під назвою `plugin:skill`, як у Claude Code.

### Нехай Enconvo вибере

Коли ви не називаєте навичку, Enconvo зіставляє ваш запит із найвідповіднішою навичкою за її `description`:

1. Ви вводите: «Підсумуй ці нотатки зустрічі у пункти дій»
2. Enconvo переглядає описи всіх доступних навичок
3. Підходить навичка `meeting-notes` («...format raw meeting transcripts into structured notes with action items...»)
4. Навичка активується, і її інструкції спрямовують відповідь

Зіставлення йде за змістом, а не лише за спільними ключовими словами, тож запит, сформульований інакше, ніж опис, або написаний іншою мовою, усе одно знаходить навичку. Щоб Агент завжди бачив навичку, закріпіть її в параметрах Агента **Інструменти й навички**; див. [Агенти](/uk/ai/agents).

### Пишіть описи, що добре збігаються

Гарне зіставлення залежить від добре написаного `description`:

| Якість | Приклад |
|---------|---------|
| **Надто розпливчастий** | «Допомагає з кодом» |
| **Надто широкий** | «Робить усе, що стосується програмування» |
| **Добрий** | «Рецензує код на помилки, проблеми безпеки та найкращі практики. Використовується, коли користувач просить рецензію коду або хоче покращити його якість. Не використовується для генерації коду чи написання нового коду.» |

Добрий опис має три частини:

- **Що вона робить**: «Рецензує код на помилки, проблеми безпеки та найкращі практики»
- **Коли спрацьовувати**: «Використовується, коли користувач просить рецензію коду»
- **Коли не спрацьовувати**: «Не використовується для генерації коду чи написання нового коду»

## Де зберігаються навички

Enconvo читає навички з кількох місць, кожне з власним обсягом:

| Обсяг | Розташування | Для чого |
|-------|----------|------------|
| **Проєкт** | `$PROJECT/.agents/skills/` (також `.enconvo/skills/`, `.claude/skills/` і `.codex/skills/`) | Навички для одного проєкту чи робочого простору |
| **Користувач** | `~/.agents/skills/` (також `~/.enconvo/skills/`, `~/.claude/skills/` і `~/.codex/skills/`) | Особисті навички для всіх ваших проєктів |
| **Система** | Постачається з Enconvo | Вбудовані навички, доступні всім |

Кожен Агент також може мати власні навички: додайте їх у **Навички** в параметрах Агента.

Якщо дві навички в різних розташуваннях мають однакову назву, обидві залишаються доступними; Enconvo їх не зливає. **Параметри → Навички** перелічує такі навички в **У кількох папках**.

### Навички проєкту

Навички проєкту зберігаються всередині папки проєкту й доступні лише тоді, коли цей проєкт активний:

```
my-project/
├── .agents/
│   └── skills/
│       ├── deploy-checklist/
│       │   └── SKILL.md
│       └── pr-template/
│           └── SKILL.md
├── src/
└── package.json
```

Використовуйте їх для навичок, що залежать від конвенцій, структури файлів чи інструментів проєкту.

### Навички користувача

Навички користувача в `~/.agents/skills/` доступні в кожному проєкті. Використовуйте їх для особистих навичок, що не належать одному проєкту:

```
~/.agents/skills/
├── email-composer/
│   └── SKILL.md
├── meeting-notes/
│   └── SKILL.md
└── code-reviewer/
    └── SKILL.md
```

## Створення навички

### За допомогою творця навичок

Найшвидший спосіб створити навичку — вбудований творець:

```
/skill-creator
```

Творець проводить вас через:

1. Що робить навичка
2. Коли вона має спрацьовувати
3. Чи має вона бути лише з інструкціями, чи містити скрипти

Лише інструкції — типовий і рекомендований підхід. Додавайте скрипти, лише коли потрібна детермінована поведінка або зовнішні інструменти.

### Вручну

Створіть папку з файлом `SKILL.md`:

<Steps>
  <Step title="Створіть каталог навички">
    ```bash
    mkdir -p ~/.agents/skills/my-skill
    ```
  </Step>
  <Step title="Напишіть SKILL.md">
    ```bash
    cat > ~/.agents/skills/my-skill/SKILL.md << 'EOF'
    ---
    name: my-skill
    description: Summarize selected text into bullet points. Use when the user asks for a summary or key takeaways. Do not use for translation or rewriting tasks.
    ---

    ## Instructions

    1. Read the selected text from the user's input.
    2. Identify the 3-5 most important points.
    3. Return a bullet-point summary.
    4. Keep each bullet under 20 words.
    EOF
    ```
  </Step>
  <Step title="Перевірте, що вона з’явилася">
    Enconvo виявляє зміни навичок автоматично. Якщо нова навичка не з’являється, перезапустіть Enconvo.
  </Step>
</Steps>

### Пишіть інструкції

Тіло `SKILL.md` під frontmatter містить інструкції, яких дотримується ШІ. Пишіть їх як чіткі кроки в наказовому способі:

````markdown
---
name: changelog-generator
description: Generate a changelog from git commits. Use when the user asks to create a changelog, release notes, or commit summary. Do not use for general git operations.
---

## Instructions

1. Read the git log for the specified date range or number of commits.
2. Group commits by category:
   - **Features**: New functionality (commits starting with "feat:")
   - **Fixes**: Bug fixes (commits starting with "fix:")
   - **Breaking Changes**: Changes that break backward compatibility
   - **Other**: Everything else
3. For each commit, write a user-facing description (not the raw commit message).
4. Format as markdown with version header, date, and categorized bullet points.
5. Highlight breaking changes with a warning callout.

## Output Format

```
## v1.2.0 (2024-01-15)

### Features
- Added dark mode support for all pages
- New export to PDF option in reports

### Fixes
- Fixed login timeout on slow connections
- Resolved duplicate notification issue

### Breaking Changes
⚠️ API endpoint `/v1/users` now requires authentication
```
````

### Поради для добрих навичок

- **Тримайте кожну навичку зосередженою.** Одна навичка робить одну справу. Навичку, що робить забагато, складніше правильно запускати й підтримувати. Якщо ви пишете 10 чи більше кроків, що охоплюють кілька завдань, розділіть її на окремі навички.
- **Будьте конкретні щодо вводу.** Вкажіть точно, звідки береться ввід: «Прочитай виділений текст», «Розбери прикріплений файл», «Використай URL із повідомлення користувача».
- **Визначте формат виводу.** Додайте конкретний приклад того, як має виглядати результат, щоб результати лишалися послідовними.
- **Опрацюйте крайні випадки.** Додайте інструкції для поширених крайніх випадків: «Якщо комітів не знайдено, повідом, що діапазон порожній» або «Якщо ввід не є коректним JSON, попроси користувача перевірити формат».
- **Пишіть кроки в наказовому способі.** Чітко визначайте ввід, кроки та очікуваний результат. Розпливчасті інструкції дають нестабільні результати.
- **Віддавайте перевагу інструкціям, а не скриптам.** Інструкції звичайною мовою легше писати, налагоджувати й змінювати. Використовуйте скрипти, лише коли потрібна детермінована поведінка або зовнішні інструменти.
- **Використовуйте чіткі межі.** В описі вкажіть і те, що навичка має обробляти, і те, чого не має.
- **Перевіряйте описи тригерів.** Спробуйте різні запити, щоб переконатися, що навичка спрацьовує, коли треба, і не спрацьовує, коли не треба.
- **Версіонуйте свої навички.** Тримайте навички, спільні для команди, у системі контролю версій (git), щоб відстежувати зміни, відкочувати їх і співпрацювати.

## Додавання скриптів

Для навичок, яким потрібна виконувана логіка, додайте папку `scripts/`:

```
my-skill/
├── SKILL.md
└── scripts/
    └── fetch_data.sh
```

Посилайтеся на скрипти у своєму `SKILL.md`:

````markdown
---
name: api-checker
description: Check API endpoint health and response times.
---

## Instructions

1. Run the health check script:
   ```bash
   bash scripts/fetch_data.sh $URL
   ```
2. Parse the JSON output.
3. Report status, response time, and any errors.
````

### Коли використовувати скрипти

| Використовуйте скрипти, коли | Використовуйте лише інструкції, коли |
|-----------------|---------------------------|
| Потрібен детермінований вивід (точні формати, обчислення) | Завдання здебільшого про міркування та мову |
| Ви взаємодієте із зовнішніми API чи базами даних | Завдання використовує лише вбудовані можливості ШІ |
| Потрібно програмно обробляти чи перетворювати дані | Завдання про написання, підсумовування чи аналіз |
| Потрібна автентифікація чи робота з обліковими даними | Самих інструкцій достатньо |

## Додавання довідкових матеріалів

Додайте файли документації чи контексту, до яких навичка може звертатися:

```
my-skill/
├── SKILL.md
├── references/
│   ├── api-docs.md
│   └── examples.md
└── scripts/
    └── run.sh
```

Посилайтеся на них в інструкціях:

```markdown
Consult `references/api-docs.md` for the API schema before making requests.
```

Довідкові матеріали корисні для:

- документації API, якої має дотримуватися навичка
- посібників зі стилю чи брендових настанов
- прикладів коду та шаблонів
- знань предметної галузі

## Інсталювання навичок

Використайте `/skill-installer`, щоб встановити навичку з магазину навичок Enconvo або з GitHub. Він також може встановлювати зі Skills.sh, ClawHub і прямих URL-адрес ZIP.

### З магазину навичок Enconvo

Знайдіть навичку за назвою й встановіть її:

```
/skill-installer pdf
```

Це шукає в магазині навичок Enconvo й встановлює відповідну навичку. Enconvo автоматично виявляє щойно встановлені навички.

### З GitHub

Встановіть навичку прямо з URL-адреси репозиторію GitHub:

```
/skill-installer https://github.com/anthropics/skills/tree/main/skills/pptx
```

URL-адреса може вказувати на підпапку, тож можна встановити одну навичку з більшого репозиторію, не клонуючи його весь.

### З папки на вашому Mac

1. Відкрийте **Параметри → Навички** й натисніть **Імпортувати**.
2. Виберіть папку, що містить підпапки навичок, кожна з `SKILL.md`.

Enconvo додає папку до місць, звідки читає навички, і її навички стають спільними для всіх Агентів. Щоб припинити використовувати папку, виберіть її в меню джерел, потім **Вилучити папку**. Сама папка залишається на диску.

## Навички зі збереженими кроками

Кожен збережений Робочий процес також є навичкою з власним `SKILL.md`, а навичка може зберігати кроки завдання, яке вона вже виконувала. Коли ви запускаєте таку навичку, її збережені кроки виконуються першими, без основної моделі, що швидше й дешевше. Крок, який більше не підходить, наприклад кнопка, що змінила місце, виправляється за власними нотатками та знімками екрана навички. Лише коли це не вдається, Агент виконує завдання за `SKILL.md`.

У **Ваші навички** навичка з позначкою **Спершу виконує збережені кроки** має кроки; з позначкою **Лише інструкції** — не має. **Історія** кожної навички показує, як минали її запуски й чого вона навчилася, а також дає змогу відновити попередню версію.

### Перетворіть запис на навичку

Запис завдання, яке ви виконали, можна перетворити на навичку. Кожна записана дія стає перевіреним кроком, а її знімок екрана зберігається для виправлень. Навичка залишається **Чернеткою**, доки її запуск не спрацює.

### Запускайте скрипт як крок

Навичка може тримати скрипт [Режиму коду](/uk/configuration/code-mode) у власній папці `scripts` і запускати його як один зі своїх кроків, тож завдання з багатьма викликами інструментів виконується як один крок.

## Нехай навички вчаться, як ви працюєте

Навички можуть вчитися, як вам подобається виконувати завдання, так само як Спогади вчаться фактів. Відкрийте **Параметри → Пам’ять** і ввімкніть **Засвоювати способи**:

- Коли ви виправляєте те, як було виконано завдання, або крок довелося виправити, навичка засвоює це одразу. У чаті з’являється примітка **Засвоєно** з **Скасувати**.
- Коли завдання трапляється вдруге, воно стає новою навичкою.
- Перегляд пам’яті та Впорядкування пам’яті також опікуються навичками.

У розділі **Під час зміни кроків** виберіть **Застосовувати одразу** або **Спершу запитати**, щоб зміна кроків навички чекала, поки ви натиснете **Застосувати** у її примітці. Підводні камені в обох випадках додаються одразу. Платежі, надсилання та видалення завжди питають вас першими, а ключі й паролі ніколи не засвоюються.

## Керування навичками

### Перегляд навичок

**Параметри → Навички** перелічує навички, спільні для всіх Агентів. Виберіть вигляд угорі:

| Вигляд | Що показує |
| --- | --- |
| **Усі навички** | Кожну навичку один раз, навіть якщо кілька папок мають її копію |
| **Увімкнено, ніколи не використовувалося** | Навички, які Агентам пропонуються в кожному чаті, але ще не використані |
| **У кількох папках** | Навички з копією більше ніж в одній папці, наприклад для Claude Code і Codex |
| **Вимкнено** | Навички, яких Агенти не отримують |

Шукайте, фільтруйте за джерелом (**Усі джерела**, **Вбудований**, **З плагінів** або одна папка) чи сортуйте за **За назвою (від А до Я)** або **Востаннє використано**.

### Оновлення навичок

- **Навички з магазину**: запустіть `/skill-installer` знову, щоб перевірити наявність новішої версії.
- **Навички з GitHub**: запустіть інсталятор знову з тією самою URL-адресою.
- **Ваші власні навички**: редагуйте файл `SKILL.md` напряму. Enconvo автоматично виявляє зміну.

### Вимкнення навички

Навичку можна вимкнути, не видаляючи її:

1. Відкрийте **Параметри → Навички**.
2. Знайдіть навичку.
3. Вимкніть її перемикач.

Агенти не можуть використовувати вимкнену навичку, ні за назвою, ні за зіставленням, доки ви не ввімкнете її знову. Профіль застосунку, що закріплює навичку, усе одно може її використовувати.

## Приклади навичок

### Рецензент коду

```markdown
---
name: code-reviewer
description: Review code for bugs, security issues, and best practices. Use when the user asks for a code review or wants to improve code quality. Do not use for code generation or writing new code.
---

## Instructions

1. Read the provided code carefully.
2. Check for:
   - Logic errors and edge cases
   - Security vulnerabilities (injection, XSS, etc.)
   - Performance issues
   - Code style and readability
3. Provide feedback as a numbered list.
4. For each issue, include:
   - Severity (Critical / Warning / Suggestion)
   - Line reference
   - Explanation and fix
```

### Нотатки зустрічі

```markdown
---
name: meeting-notes
description: Format raw meeting transcripts into structured notes with action items. Use when the user provides meeting notes, transcripts, or asks to organize meeting content. Do not use for scheduling or calendar tasks.
---

## Instructions

1. Parse the meeting transcript or raw notes.
2. Extract and organize into sections:
   - **Attendees**: List all participants
   - **Key Decisions**: Bullet-point decisions made
   - **Discussion Summary**: 3-5 sentence overview
   - **Action Items**: Table with Owner, Task, Deadline
3. Use markdown formatting for readability.
```

### Повідомлення git-коміту

````markdown
---
name: commit-message
description: Generate conventional commit messages from staged changes. Use when the user asks for a commit message or wants to commit changes. Do not use for general git operations like branching or merging.
---

## Instructions

1. Read the staged diff (use `git diff --staged`).
2. Identify the type of change:
   - feat: New feature
   - fix: Bug fix
   - docs: Documentation
   - refactor: Code restructuring
   - test: Adding tests
   - chore: Maintenance
3. Write a commit message following Conventional Commits format:
   ```
   type(scope): concise description

   - Detail 1
   - Detail 2
   ```
4. Keep the subject line under 72 characters.
5. Include a body only if the change needs explanation.
````

### Генератор документації API

````markdown
---
name: api-docs
description: Generate API documentation from source code. Use when the user asks to document an API, endpoint, or function. Do not use for general code documentation or README files.
---

## Instructions

1. Read the source code file(s) provided.
2. For each endpoint or public function, document:
   - **Method & Path** (for HTTP) or **Signature** (for functions)
   - **Description**: What it does in one sentence
   - **Parameters**: Name, type, required/optional, description
   - **Response**: Structure and example
   - **Errors**: Possible error codes and meanings
3. Format as markdown with code examples.
4. Include a curl example for each HTTP endpoint.

## Output Format

### `POST /api/users`

Create a new user account.

**Parameters:**

| Name | Type | Required | Description |
|------|------|----------|-------------|
| email | string | Yes | User's email address |
| name | string | Yes | Display name |

**Response (201):**
```json
{ "id": "usr_123", "email": "user@example.com", "name": "John" }
```
````
