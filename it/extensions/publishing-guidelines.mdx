Questa pagina è per gli sviluppatori che stanno per inviare un plugin allo store dei plugin di Enconvo. Elenca cosa controllano i revisori, i materiali di revisione da inviare con ogni versione, una checklist da seguire prima di `plugin publish` e cosa succede dopo l'invio.

Enconvo esamina ogni versione inviata allo store dei plugin prima che qualcun altro possa installarla. Queste linee guida valgono per ogni tipo di plugin accettato dallo store: plugin Enconvo, Codex, Claude Code e portabili, compresi quelli composti solo da competenze. Seguono le [linee guida sui plugin di OpenAI](https://developers.openai.com/apps-sdk/app-submission-guidelines), quindi un plugin che le rispetta è anche quasi pronto per il portale dei plugin di OpenAI.

## Controlla prima il tuo plugin

Prima di inviare, esegui:

```sh
npx -p @enconvo/api enconvo plugin validate            # the store's rules
npx -p @enconvo/api enconvo plugin validate --openai   # also OpenAI's portal rules
npx -p @enconvo/api enconvo plugin scan                # starts the MCP server and checks its tools
```

`validate` individua ciò che si può verificare in automatico, mentre `scan` controlla gli strumenti di un plugin con un server MCP; [Validation Codes](/extensions/validation-codes) spiega ogni problema segnalato. Il resto lo controllano i revisori a mano, come descritto di seguito.

## Scopo e qualità

- Il plugin fa qualcosa di utile che Enconvo non sa già fare, e lo fa in modo completo. Le versioni segnaposto, solo dimostrative o di prova vengono respinte.
- Si comporta in modo prevedibile. Quando qualcosa va storto, come un errore di rete, un permesso mancante o un input errato, dice che cosa è successo invece di fallire in silenzio.
- Usa solo codice, nomi, icone e contenuti di tua proprietà o che hai la licenza di usare. Non imita un altro prodotto e non lascia intendere che Enconvo o altri lo approvino.

## Nome, descrizione e scheda

- **Nome e titolo**: chiari e specifici. Evita una singola parola generica e non aggiungere "MCP", "MCP Server" o "Plugin" al nome di un'azienda.
- **Descrizione**: dice con precisione cosa fa il plugin. Niente confronti con altri prodotti, affermazioni che non puoi dimostrare, né prezzi, sconti o offerte di prova gratuita.
- **Icona e schermate**: l'icona è un PNG, JPEG, WebP o GIF fino a 5 MB. Fino a 8 schermate vanno in una cartella `metadata/` e vengono mostrate in ordine di nome file. Mostrano il plugin così come funziona davvero.
- **Assistenza**: dai alle persone un modo per contattarti: `interface.websiteURL` e `interface.supportURL`, oppure `homepage` o `repository` per il sito web. Un plugin Claude Code può usare invece `supportUrl` e `documentationUrl`. La pagina dello store mostra questi link prima che qualcuno installi il plugin.
- **Versione**: aumentala a ogni aggiornamento. Mentre un aggiornamento è in revisione, lo store continua a offrire la versione precedente. `plugin publish` chiede allo store quale versione ha pubblicato prima di compilare o caricare qualsiasi cosa, e si ferma indicando la versione successiva da usare quando la tua non è più alta.

## Strumenti MCP

Quando il plugin include un server MCP, i revisori leggono i suoi strumenti come li leggerà il modello di IA.

- I **nomi** sono verbi semplici che dicono cosa fa lo strumento, come `get_order_status`, e sono univoci all'interno del server. Niente gergo né abbreviazioni non spiegate.
- Le **descrizioni** spiegano cosa fa lo strumento, cosa modifica e cosa non può fare, e corrispondono al suo schema di input e al comportamento reale. Non dicono al modello di preferire questo plugin, di chiamare altri plugin o di chiamare lo strumento per qualsiasi cosa.
- **Un'operazione per strumento**, ciascuno con il proprio schema di input.
- Le **annotazioni** sono impostate esplicitamente su ogni strumento:

| Annotazione | `true` quando lo strumento | `false` quando |
|---|---|---|
| `readOnlyHint` | legge, calcola o mostra solo un'anteprima | modifica qualcosa: scrive, salva un file, invia, pubblica, carica, mette in coda un lavoro o avvia un processo |
| `destructiveHint` | elimina, sovrascrive, annulla o invia qualcosa che non si può riprendere, anche se l'utente potrebbe annullare | si limita ad aggiungere |
| `openWorldHint` | raggiunge contenuti pubblici o aperti, come una ricerca sul web, oppure invia a qualsiasi indirizzo | resta all'interno di un account, uno spazio di lavoro o un catalogo delimitato, anche se ospitato altrove |

Enconvo si affida a queste annotazioni. Uno strumento con `readOnlyHint: true` viene eseguito senza chiedere all'utente e insieme ad altre letture. Uno strumento con `destructiveHint: true` chiede prima all'utente, a meno che non abbia dato all'agente accesso completo. Uno strumento che modifica qualcosa ma si dichiara di sola lettura viene respinto.

`enconvo plugin scan` avvia il server MCP del plugin, elenca i suoi strumenti con le annotazioni e indica ogni strumento che ne omette una ([`annotations_required`](/extensions/validation-codes#mcp-server-scan)).

Uno strumento che mostra una propria interfaccia indica la sua vista, una risorsa `ui://`, in `_meta.ui.resourceUri`, e la vista dichiara i domini che raggiunge in `_meta.ui.csp` (`connectDomains`, `resourceDomains`, `frameDomains`). Sono le chiavi MCP Apps che ogni host legge. Enconvo legge anche `_meta["openai/outputTemplate"]` e `_meta["openai/widgetCSP"]` di ChatGPT e dà a una vista scritta per ChatGPT (`text/html+skybridge`, o uno strumento indicato solo da `openai/outputTemplate`) l'API `window.openai` che richiama, così un plugin creato per ChatGPT mostra la sua interfaccia in Enconvo senza modifiche. Imposta anche le chiavi MCP Apps, in modo che la mostrino anche gli altri host. `scan` legge ogni vista come fa Enconvo e segnala quando una è impostata solo alla maniera di OpenAI.

## Dati e privacy

- **Chiedi solo ciò che serve al compito.** Gli input degli strumenti sono specifici del compito. Non chiedere l'intera conversazione, i messaggi precedenti o dati di profilo generici "per sicurezza".
- **Restituisci solo ciò che risponde alla richiesta.** Lascia fuori dai risultati degli strumenti id interni, dati di traccia e output di debug.
- **Non raccogliere mai** dati di carte di pagamento, cartelle cliniche, documenti d'identità governativi come i numeri di previdenza sociale, né password, chiavi API e codici monouso tramite gli input degli strumenti. Le credenziali vanno nelle preferenze del plugin, dove Enconvo le conserva.
- **Informativa sulla privacy.** Un plugin che invia dati a un server ha bisogno di un'informativa sulla privacy pubblicata che dica cosa raccoglie, perché, chi li riceve, per quanto tempo vengono conservati e come le persone possono eliminarli. Inserisci il suo indirizzo in `interface.privacyPolicyURL` e, se li hai, i termini di servizio in `interface.termsOfServiceURL`. La pagina dello store li collega entrambi.
- **Nessun tracciamento** delle persone, delle loro richieste o del loro utilizzo oltre a quanto serve al plugin per funzionare e a quanto dichiarato nella sua informativa sulla privacy.
- **Tieni i segreti fuori dal pacchetto.** Chiunque può scaricarlo. I file `.env` vengono esclusi automaticamente, ma verifica che nessun'altra chiave o file privato finisca al suo interno.

## Accesso e account di prova

Se il plugin richiede un account, l'accesso è esplicito e chiede solo i permessi necessari. I revisori devono poterlo provare senza creare un account né ricevere un codice a due fattori, quindi forniscigli un account demo con dati di esempio:

```sh
npx -p @enconvo/api enconvo plugin publish --review-notes "Sign in as review@example.com with the password …"
```

Le note per i revisori vanno solo ai revisori di Enconvo. Non fanno parte del pacchetto né della scheda dello store.

## Commercio

Un plugin può funzionare con un account che le persone già pagano e può indicare quando una funzione richiede un piano diverso. Se vende qualcosa o accetta pagamenti, dillo nei materiali di revisione (`commerce` e `commerce_description`, più avanti): cosa viene venduto e dove si paga. Le persone pagano sul tuo sito; il plugin non nasconde addebiti né fa pagare agli utenti di Enconvo più che a tutti gli altri.

Il portale di OpenAI è più severo. Accetta solo plugin che vendono beni fisici, senza abbonamenti, crediti o altri prodotti digitali. Controlla le sue [regole sul commercio](https://developers.openai.com/apps-sdk/app-submission-guidelines) prima di inviare lì.

## Sicurezza

- Il plugin è adatto a un pubblico generale, adolescenti compresi, e non si rivolge a bambini sotto i 13 anni.
- Fa ciò che l'utente ha chiesto e nient'altro: niente contenuti non correlati, reindirizzamenti o pubblicità.
- Le sue descrizioni, i suoi prompt e le sue competenze non chiedono mai segreti, non spostano denaro o dati senza il consenso dell'utente, non cercano di aggirare le protezioni di Enconvo né nascondono ciò che fa il plugin, anche tramite istruzioni codificate.
- Non estrae dati dai siti web né incapsula altri servizi in violazione dei loro termini, né aggira i loro limiti di frequenza e i controlli di accesso.
- Non vende né abilita nulla di ciò che compare nell'elenco di [beni e servizi vietati](https://developers.openai.com/apps-sdk/app-submission-guidelines) di OpenAI, come armi, droghe, gioco d'azzardo, contenuti per adulti, malware o frodi finanziarie.

## Materiali di revisione

I materiali di revisione dicono ai revisori cosa provare: i prompt che il plugin deve gestire, quelli che deve lasciare perdere e un breve video dimostrativo. Sono memorizzati con ogni versione e mostrati solo ai revisori.

In un plugin Codex, Claude Code o portabile vanno dove li legge il portale di OpenAI, sotto `extensions["com.openai"]` di un unico `plugin.json`. OpenAI li importa da `.codex-plugin/plugin.json` quando il plugin ne ha uno, come lo crea `enconvo plugin create`; dal `plugin.json` radice quando questo ha un proprio `extensions["com.openai"]` o non c'è un manifest Codex; e da `.claude-plugin/plugin.json` in un plugin creato solo per Claude Code. Non aggiungere `extensions["com.openai"]` al `plugin.json` radice solo per questi: Codex ignorerebbe allora la scheda in `.codex-plugin/plugin.json`. `enconvo plugin validate --openai` indica il manifest a cui appartengono.

```json
{
  "name": "notes",
  "version": "1.2.0",
  "extensions": {
    "com.openai": {
      "review": {
        "test_cases": {
          "positive": [
            {
              "description": "Finds a note by topic",
              "prompt": "Find my notes about the Q3 launch",
              "tools_triggered": "search_notes, read_note",
              "expected_behavior": "Lists the matching notes and quotes the most relevant one"
            }
          ],
          "negative": [
            { "description": "Unrelated question", "prompt": "What's the weather in Paris?" }
          ]
        },
        "demo_recording_url": "https://example.com/notes-demo.mp4",
        "commerce": false
      },
      "publication": {
        "release_notes": "Search now matches note titles."
      }
    }
  }
}
```

In un plugin Enconvo, lo stesso oggetto `review` va al livello superiore di `package.json`.

| Campo | Cosa contiene |
|---|---|
| `test_cases.positive` | I prompt che il plugin deve gestire, ciascuno con una `description`, il `prompt`, `expected_behavior` e i `tools_triggered`. Facoltativi: `file_attachment_urls` e `expected_output_url`. |
| `test_cases.negative` | I prompt che il plugin deve lasciare a qualcos'altro, ciascuno con una `description` e il `prompt`. |
| `demo_recording_url` | Un video dei prompt e degli strumenti principali. |
| `commerce`, `commerce_description` | Se il plugin vende qualcosa, e cosa e dove. |
| `publication.release_notes` | Cosa è cambiato. `plugin publish` le usa come changelog dello store a meno che tu non passi `-m`. |

Ogni elenco contiene fino a 20 casi. I campi di testo contengono fino a 4.000 caratteri e ogni indirizzo è un indirizzo `https://` che i revisori possono aprire. `validate` e `publish` rifiutano materiali che violano questi limiti.

I dati di accesso non vanno mai nel pacchetto, perché chiunque può scaricarlo. `validate` e `publish` rifiutano un `review` che contiene `test_credentials` o `reviewer_instructions`; passali invece con `--review-notes`, oppure nel modulo Review details della dashboard di OpenAI.

In `plugin.json`, `publication` può contenere anche ciò che il portale di OpenAI importa per la scheda, e `validate --openai` lo controlla come fa il portale. Enconvo mostra `translations` nella lingua dell'interfaccia per un plugin installato e prima di installarne uno da una fonte; le pagine dello store di Enconvo non le usano ancora:

| Campo | Cosa contiene |
|---|---|
| `countries` | Dove il plugin è disponibile, come codici paese maiuscoli, ad esempio `["US", "GB"]`. `[]` lo rende disponibile ovunque. |
| `translations` | Testo della scheda per lingua, ad esempio `{"fr-FR": {"subtitle": "…", "description": "…"}}`. Un sottotitolo è una riga di al massimo 30 caratteri, una descrizione fino a 4.000. |

Un campo impostato su `null` mantiene il valore già salvato nella dashboard di OpenAI. I casi di test a livello di plugin sono per un plugin con esattamente un server MCP.

L'invio finale a OpenAI di un plugin con un server MCP o un'app richiede esattamente 5 casi positivi e 3 negativi, una registrazione demo e le note di rilascio; un plugin con sole competenze richiede solo le note di rilascio. `validate --openai` elenca ciò che manca come avvisi, perché il caricamento del portale accetta un plugin senza di essi e li chiede solo all'invio finale.

## Checklist di invio

Prima di eseguire `plugin publish`:

- `plugin validate` non segnala errori e hai letto i suoi avvisi.
- `version` è più alta dell'ultima versione che hai pubblicato e ogni manifest nel pacchetto riporta lo stesso nome e la stessa versione.
- Per un aggiornamento, `plugin validate --previous` con lo zip della versione precedente non segnala nulla che non intendessi: un aggiornamento sostituisce l'intero plugin, quindi una competenza o un server MCP che omette viene rimosso (`plugin_components_removed`).
- Il titolo, la descrizione e l'icona dicono cosa fa il plugin e le schermate lo mostrano in funzione.
- È impostato un indirizzo di homepage o di assistenza e, se il plugin invia dati da qualche parte, è collegata un'informativa sulla privacy.
- Ogni strumento MCP ha un nome e una descrizione chiari e imposta `readOnlyHint`, `destructiveHint` e `openWorldHint`, e `plugin scan` li elenca senza problemi.
- Le competenze indicano nella loro `description` quando usarle.
- Le impostazioni obbligatorie, come una chiave API, sono dichiarate come impostazioni, non richieste in chat.
- Nella cartella non ci sono chiavi, token o file privati.
- I materiali di revisione elencano i prompt da provare e quelli da lasciare perdere e, se serve l'accesso, è pronto un account demo per `--review-notes`.
- Hai installato il pacchetto dalla sua cartella (`plugin install .`) e provato i casi di test in Enconvo.

## Cosa succede dopo l’invio

1. `plugin publish` controlla il plugin e che la sua versione sia più alta di quella pubblicata dallo store, poi lo carica e invia la versione in revisione. Finché un nuovo plugin non è approvato, solo tu puoi vederlo.
2. Un revisore legge la scheda, i file del pacchetto (con ciò che è cambiato rispetto alla versione pubblicata), i materiali di revisione e le tue note, e prova i casi di test.
3. Una versione approvata compare nello store e alle copie installate viene offerto l'aggiornamento. Se una versione viene respinta, ricevi un'email con il motivo. Correggila, aumenta la versione e pubblica di nuovo.

Enconvo esamina anche le segnalazioni sui plugin pubblicati. Un plugin che risulta violare queste linee guida, anche se approvato in precedenza, può essere rimosso dallo store e al suo sviluppatore viene inviata un'email con il motivo.

## Inviare anche a OpenAI

La stessa cartella può andare al portale dei plugin di OpenAI:

```sh
npx -p @enconvo/api enconvo plugin validate --openai
npx -p @enconvo/api enconvo plugin scan --openai
npx -p @enconvo/api enconvo plugin pack --openai
```

`pack --openai` scrive lo zip che il portale accetta. Le credenziali per i revisori di OpenAI vanno nel modulo di invio del portale, mai nel pacchetto. Tieni fuori anche le tue chiavi: `pack` e `publish` escludono i file `.env` e `validate` avvisa di un file che sembra una chiave privata o un login (`archive_member_secret`).

### Nome del plugin

Il portale accetta solo lettere, cifre, `-` e `_` nel `name` del plugin, e OpenAI suggerisce lettere minuscole, cifre e trattini singoli. Codex, Claude Code ed Enconvo installano anche un nome con il punto come `acme.tools`, ma `validate --openai` e `pack --openai` lo rifiutano (`plugin_name_format`), quindi chiama `acme-tools` un plugin che intendi inviare.

### Server MCP e dominio

Dopo il caricamento, il portale si connette al server MCP del plugin ed esegue la scansione dei suoi strumenti; quando il server cambia, eseguila di nuovo lì. Raggiunge il server solo a un URL `https://` pubblico, quindi un server che gira sul computer dell'utente va prima distribuito; `scan --openai` avvisa di uno così (`mcp_server_not_remote`). All'invio finale il portale chiede tutte e tre le annotazioni su ogni strumento. Non ti chiede più di giustificarle; se la sua revisione automatica ne segnala una, puoi fare ricorso con una spiegazione. Un plugin le cui viste incorporano pagine richiede ancora una giustificazione per ogni pagina incorporata: cosa fa, perché il plugin la incorpora e chi controlla il suo dominio. Le pagine del dominio registrabile del server MCP stesso sono consentite, e tenant separati su un host condiviso contano come domini diversi. `scan --openai` elenca i domini che le tue viste incorporano (`frame_domain_explanation_required`).

Prima di poter inviare il plugin, il portale verifica che tu controlli il dominio del server MCP: ti dà un token da servire come testo semplice in `/.well-known/openai-apps-challenge` sull'host del server o su un dominio padre. `scan --openai` dice cosa rispondono quegli URL, e `scan --challenge-token <token>` controlla che uno serva esattamente il token prima di selezionare **Verify Domain**; vedi [Domain verification](/extensions/validation-codes#domain-verification).

Il portale di OpenAI collega un solo server MCP per plugin per analizzarlo e revisionarlo, quindi `validate --openai` avvisa di un plugin che ne ha di più. Lo stesso server dichiarato per Codex in `mcp.json` e per Claude Code in `.mcp.json` conta una volta sola.

### Aggiornare un plugin pubblicato

Per aggiornare un plugin che hai pubblicato lì, carica uno ZIP completo con una versione più alta e tutto ciò che intendi mantenere. Se non hai conservato lo zip della versione pubblicata, il portale te lo fornisce con **Download release ZIP** nel menu **…** di quella versione; controlla la nuova versione rispetto a esso con `validate --openai --previous <zip>`. Il portale non può aggiungere un server MCP a un plugin pubblicato che non ne aveva, né cambiare l'URL di un server pubblicato (chiedilo all'assistenza di OpenAI), e `--previous` segnala entrambi i casi; vedi [Updates](/extensions/validation-codes#updates).

### Invio finale

L'invio finale di OpenAI chiede alla scheda più di quanto faccia il caricamento, e `validate --openai` avvisa di ogni lacuna:

- `interface.longDescription` e una `interface.category`; senza una categoria, la directory elenca il plugin sotto Other.
- Per un plugin con un server MCP, `websiteURL`, `supportURL`, `privacyPolicyURL` e `termsOfServiceURL`, ciascuno un indirizzo `https://` di al massimo 1.024 caratteri.
- Una scheda tutta tua. Un plugin Claude Code con il solo `.claude-plugin/plugin.json` ne ottiene una che il portale compila con valori predefiniti (`claude_format_normalized`), quindi aggiungi un `.codex-plugin/plugin.json` con un `interface` per scriverla tu.
- Schermate solo quando il server MCP ha una propria interfaccia: un PNG o JPEG per ogni prompt iniziale, larghi esattamente 706 pixel e alti da 400 a 860 pixel. Il portale lo decide in base alla sua scansione, quindi `scan --openai` rifiuta le schermate quando nessuno strumento mostra un'interfaccia (`screenshots_not_allowed`). La directory di OpenAI non mostra più le schermate e presenta un plugin tramite i suoi prompt iniziali, quindi scrivili con cura.

La directory mostra il nome dello sviluppatore della tua identità OpenAI verificata, qualunque cosa dica `interface.developerName`. Per i codici, vedi [OpenAI's final submission](/extensions/validation-codes#openai’s-final-submission).
