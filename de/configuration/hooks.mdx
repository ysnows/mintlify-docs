title: "Hooks"
description: "Führe automatisch einen Shell-Befehl aus oder sende einen Webhook, wenn ein Agent startet, ein Tool nutzt oder fertig wird."
---

Hooks führen einen Shell-Befehl aus oder senden eine HTTP-Anfrage, wenn in Enconvo etwas passiert, etwa wenn ein Agent startet, abschließt, fehlschlägt oder ein Tool nutzt. Du richtest sie in einer JSON-Datei ein, sodass du Benachrichtigungen, Protokolle, lokale Automatisierung oder Integrationen hinzufügen kannst, ohne eine Erweiterung zu bauen.

<Note>
Die meisten Hooks sind Fire-and-forget: Sie laufen im Hintergrund und blockieren Enconvo nicht. `PreToolUse`, `Stop` und `SubagentStop` sind bei Agentenläufen die Ausnahme. Der Agent wartet auf sie, sodass sie einen Tool-Aufruf blockieren oder den Agenten zurück an die Arbeit schicken können. Siehe [Blockierende Hooks](#blockierende-hooks).
</Note>

## Schnellstart

<Steps>
  <Step title="Den Hooks-Ordner erstellen">
    ```bash
    mkdir -p ~/.enconvo
    ```
  </Step>

  <Step title="~/.enconvo/hooks.json erstellen">
    ```json
    {
      "hooks": {
        "UserPromptSubmit": [
          {
            "hooks": [
              {
                "type": "command",
                "command": "echo 'Agent status changed' >> /tmp/enconvo-hooks.log"
              }
            ]
          }
        ]
      }
    }
    ```
  </Step>

  <Step title="Einen Agenten auslösen">
    Starte einen beliebigen Agenten oder Chat-Befehl. Wenn sich sein Status ändert, führt Enconvo den
    konfigurierten Befehl aus und hängt eine Zeile an `/tmp/enconvo-hooks.log` an.
  </Step>
</Steps>

## Konfigurationsdatei

Hooks liegen in:

```text
~/.enconvo/hooks.json
```

Enconvo liest außerdem die ältere Datei unter `~/.config/enconvo/hooks.json`, wenn die neue Datei nicht existiert. Existieren beide Dateien, gewinnt `~/.enconvo/hooks.json`.

Die Datei wird bei jedem ausgelösten Ereignis neu gelesen, sodass du Hooks bearbeiten kannst, während Enconvo läuft. Ein Neustart ist nicht nötig.

## Hooks in den Einstellungen verwalten

Öffne **Einstellungen → Hooks**, um die Hooks in `~/.enconvo/hooks.json` nach Ereignis gruppiert zu sehen. Schalte einen Eintrag mit seinem Schalter ein oder aus oder klicke auf **hooks.json öffnen**, um die Datei zu bearbeiten. Beim Aus- oder Einschalten eines Eintrags wird `enabled: false` oder `enabled: true` in diesen Eintrag geschrieben, ohne seinen Befehl oder Webhook zu ändern.

## Hooks aus Plugins

Plugins für Claude Code und Codex, etwa context-mode, können eigene Hooks mitbringen. Sobald du sie erlaubst, laufen sie wie in Claude Code: beim Start eines Chats, rund um jede Nachricht, jeden Tool-Aufruf und jede Verdichtung sowie wenn eine Antwort fehlschlägt oder der Agent fertig wird.

1. Installiere das Plugin über **Plugins** oder gib einem Agenten im Chat das GitHub-Repository, die Git-Adresse, das Zip oder das npm-Paket des Plugins. Er bietet die Installationskarte des Plugins an.
2. Hake **Seine Hooks ausführen lassen** an, bevor du installierst. Ein ohne diese Option installiertes Plugin zeigt, dass seine Hooks aus sind; klicke später bei ihm auf **Hooks erlauben**, um sie einzuschalten.

Ändert ein Plugin-Update seine Hooks, laufen sie nicht mehr, bis du sie prüfst und erneut erlaubst. Hooks, die Enconvo nicht ausführen kann, werden auf der Karte als in Enconvo nicht ausgeführt aufgelistet.

## Wie Hooks funktionieren

Wenn ein Ereignis ausgelöst wird, macht Enconvo Folgendes:

1. Lädt `~/.enconvo/hooks.json`.
2. Greift nur dann auf `~/.config/enconvo/hooks.json` zurück, wenn die neue Datei fehlt.
3. Findet Einträge im Objekt `hooks` der obersten Ebene, deren Schlüssel zum Ereignisnamen passt.
4. Wendet den optionalen regulären Ausdruck `matcher` an.
5. Überspringt Einträge, bei denen `enabled` auf `false` steht.
6. Führt jeden konfigurierten Hook gleichzeitig aus.

Die Ereignisnamen der Hooks folgen dem Lebenszyklus-Satz von Claude Code und Codex: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `Stop` und `SubagentStop`. Die alten Enconvo-Ereignisnamen und das alte flache JSON-Format funktionieren bei bestehenden Installationen weiterhin, neue Einträge verwenden aber das umschlossene Format im Codex-Stil.

## Konfigurationsreferenz

```json
{
  "hooks": {
    "event_name": [
      {
        "matcher": "optional_regex_filter",
        "enabled": true,
        "hooks": [
          { "type": "command", "command": "..." },
          { "type": "http", "url": "..." }
        ]
      }
    ]
  }
}
```

| Feld | Typ | Erforderlich | Beschreibung |
|-------|------|----------|-------------|
| `hooks` | object | Ja | Ereignis-Map, nach Ereignisnamen geschlüsselt. |
| `event_name` | string | Ja | Ereignis, auf das gehört wird. Verwende es als Schlüssel in `hooks`. |
| `matcher` | string | Nein | Filter als regulärer Ausdruck. Bei Tool-Ereignissen passt er auf `toolName`, `toolTitle` oder `path`; bei anderen Ereignissen auf den Namen des Hook-Ereignisses. |
| `enabled` | boolean | Nein | Auf `false` setzen, um den Eintrag in der Konfiguration zu behalten, aber nicht auszuführen. Standardmäßig `true`. |
| `hooks` | array | Ja | Auszuführende Befehls- und HTTP-Hooks. |

### Befehls-Hook

Ein Befehls-Hook führt einen Shell-Befehl aus. Enconvo schreibt die Ereignisdaten als JSON auf die Standardeingabe (stdin) des Befehls.

```json
{
  "type": "command",
  "command": "bash ~/.enconvo/hooks/on-status-change.sh",
  "timeout": 30000
}
```

| Feld | Typ | Standard | Beschreibung |
|-------|------|---------|-------------|
| `type` | `"command"` | - | Erforderlicher Hook-Typ. |
| `command` | string | - | Auszuführender Shell-Befehl. |
| `timeout` | number | `30000` | Zeitlimit in Millisekunden. |

### HTTP-Hook

Ein HTTP-Hook sendet die Ereignisdaten als JSON-Anfragetext.

```json
{
  "type": "http",
  "url": "https://example.com/webhook",
  "method": "POST",
  "headers": {
    "Authorization": "Bearer your-token"
  },
  "timeout": 30000
}
```

| Feld | Typ | Standard | Beschreibung |
|-------|------|---------|-------------|
| `type` | `"http"` | - | Erforderlicher Hook-Typ. |
| `url` | string | - | URL des HTTP-Endpunkts. |
| `method` | string | `"POST"` | HTTP-Methode. |
| `headers` | object | `{}` | Zusätzliche Anfrage-Header. |
| `timeout` | number | `30000` | Zeitlimit in Millisekunden. |

## Blockierende Hooks

Bei einem Agenten- oder Bot-Lauf laufen drei Ereignisse als blockierende Hooks. Der Agent wartet auf jeden passenden Hook (sie laufen parallel), bevor er weitermacht, und liest ihr Ergebnis genauso wie Claude Code und Codex.

| Ereignis | Wann | Was der Hook tun kann |
|-------|------|----------------------|
| `PreToolUse` | Direkt bevor ein Tool-Aufruf läuft. Der `matcher` wird gegen Tool-Name, Titel und Routenpfad geprüft. | Den Aufruf blockieren oder seine Eingabe umschreiben. |
| `Stop` | Direkt bevor der Agent seinen Zug mit einer Antwort beendet. | Den Agenten mit einer Anweisung zurück an die Arbeit schicken. |
| `SubagentStop` | Direkt bevor ein Unteragent fertig wird. | Den Unteragenten mit einer Anweisung zurück an die Arbeit schicken. |

Ein Hook entscheidet auf eine von zwei Arten:

- **Exit-Code 2** blockiert. Der Text, den der Befehl nach stderr schreibt, ist die Begründung.
- **Exit-Code 0 mit JSON auf stdout.** Jede andere Ausgabe, jeder andere Exit-Code, Fehler oder Timeout entscheidet nichts, und der Lauf geht weiter, als gäbe es den Hook nicht.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Writing outside the project is not allowed."
  }
}
```

| JSON-Ausgabe | Wirkung |
|-------------|--------|
| `hookSpecificOutput.permissionDecision: "deny"` | `PreToolUse`: Der Aufruf läuft nicht. Das Modell sieht `permissionDecisionReason` als Tool-Ergebnis und kann einen anderen Weg wählen. |
| `hookSpecificOutput.permissionDecision: "ask"` | Wird wie `deny` behandelt. Enconvo hat für Hooks noch keine Bestätigungsabfrage. |
| `hookSpecificOutput.permissionDecision: "allow"` | `PreToolUse`: Der Aufruf läuft. |
| `hookSpecificOutput.updatedInput` | `PreToolUse`: Der Aufruf läuft mit dieser Eingabe statt mit der des Modells. |
| `{ "decision": "block", "reason": "..." }` | `Stop` / `SubagentStop`: Der Agent arbeitet weiter, mit `reason` als nächster Anweisung. Bei `PreToolUse` blockiert es den Aufruf. |
| `{ "decision": "approve" }` | Wie `allow`. |

HTTP-Hooks entscheiden mit einer 2xx-Antwort, deren Text dasselbe JSON ist.

Passen mehrere Hooks, gewinnt ein deny über ask, und ask gewinnt über allow. Die Begründungen werden verbunden, und das letzte `updatedInput` wird verwendet.

Ein `Stop`-Hook kann den Agenten in einem Zug höchstens 5 Mal zurückschicken. Bei der zweiten und jeder weiteren Prüfung ist `stop_hook_active` gleich `true`, sodass ein Hook den Agenten anhalten lassen kann, sobald seine Anweisung befolgt wurde. Das Blockieren durch `Stop` gilt nur, wenn der Agent normal fertig wird; ein fehlgeschlagener oder gestoppter Lauf löst `Stop` weiterhin im Hintergrund aus.

<Tip>
Der Agent wartet auf blockierende Hooks, daher verlangsamt ein langsamer `PreToolUse`-Hook jeden Tool-Aufruf, und ein langsamer `Stop`-Hook verzögert das Ende des Zugs. Halte sie schnell, setze ein kurzes `timeout` oder führe langsame Arbeit im Hintergrund aus (`command &`).
</Tip>

Blockierende Hooks erhalten die reguläre [Ereignis-Payload](#ereignis-payload) plus die Felder von Claude Code auf oberster Ebene:

```json
{
  "hook_event_name": "PreToolUse",
  "session_id": "Qx2...",
  "cwd": "/Users/you/project",
  "tool_name": "bash",
  "tool_input": { "command": "rm -rf build" },
  "tool_use_id": "call_1",
  "event": "PreToolUse",
  "sourceEvent": "agent_tool_step_changed",
  "params": { "toolName": "bash", "status": "running", "sessionId": "Qx2..." },
  "timestamp": 1742313600000
}
```

`Stop` und `SubagentStop` erhalten statt der Tool-Felder `stop_hook_active` und `last_assistant_message`. Befehls-Hooks laufen im Arbeitsverzeichnis des Agenten.

### Einen gefährlichen Befehl blockieren

```bash
#!/bin/bash
# ~/.enconvo/hooks/guard.sh
COMMAND=$(jq -r '.tool_input.command // empty')
if echo "$COMMAND" | grep -q 'rm -rf /'; then
  echo "Deleting from the filesystem root is not allowed." >&2
  exit 2
fi
```

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "bash",
        "hooks": [{ "type": "command", "command": "bash ~/.enconvo/hooks/guard.sh", "timeout": 5000 }]
      }
    ]
  }
}
```

### Den Agenten vor dem Abschluss Tests ausführen lassen

```bash
#!/bin/bash
# ~/.enconvo/hooks/require-tests.sh
[ "$(jq -r '.stop_hook_active')" = "true" ] && exit 0
echo '{"decision":"block","reason":"Run the test suite and fix any failures before you finish."}'
```

## Ereignis-Payload

Befehls-Hooks erhalten dieses JSON auf stdin. HTTP-Hooks erhalten dasselbe JSON als Anfragetext.

```json
{
  "event": "UserPromptSubmit",
  "fullEvent": "event-UserPromptSubmit",
  "sourceEvent": "run_status_changed",
  "sourceFullEvent": "event-run_status_changed",
  "params": {
    "commandKey": "agent|main",
    "runStatus": "running"
  },
  "timestamp": 1742313600000
}
```

| Feld | Beschreibung |
|-------|-------------|
| `event` | Kurzer Ereignisname. |
| `fullEvent` | Interner Ereignisname mit dem Präfix `event-`. |
| `sourceEvent` | Ursprüngliches Enconvo-Ereignis, das dieses Hook-Ereignis erzeugt hat, wenn das Ereignis zur Codex-Kompatibilität zugeordnet wird. |
| `sourceFullEvent` | Ursprünglicher interner Ereignisname mit dem Präfix `event-`. |
| `params` | Ereignisspezifische Nutzdaten. |
| `timestamp` | Unix-Zeitstempel in Millisekunden. |

Hooks im Hintergrund erhalten ebenfalls die Felder von Claude Code: `hook_event_name`, `session_id`, wenn das Ereignis eine hat, und bei Tool-Ereignissen `tool_name`, `tool_input` und `tool_use_id`.

## Verfügbare Ereignisse

| Ereignis | Parameter | Wann |
|-------|--------|------|
| `SessionStart` | `{ command, commandKey }` | Eine neue Chat-Sitzung wird erstellt. |
| `UserPromptSubmit` | `{ commandKey, runStatus, status?, sessionId? }` | Ein Agenten-, Chat- oder Bot-Lauf startet durch eine Benutzereingabe. |
| `PreToolUse` | `{ toolCallId, toolName, toolTitle?, status, sessionId?, commandKey? }` | Ein Tool-Aufruf beginnt. Blockierend bei Agentenläufen. |
| `PermissionRequest` | `{ toolCallId, toolName, toolTitle?, status, sessionId?, commandKey? }` | Ein Tool-Aufruf erreicht einen Berechtigungs- oder Abgelehnt-Zustand. |
| `PostToolUse` | `{ toolCallId, toolName, toolTitle?, status, sessionId?, commandKey? }` | Ein Tool-Aufruf gelingt, schlägt fehl, schließt ab oder wird abgelehnt. |
| `Stop` | `{ commandKey, runStatus, status?, sessionId? }` | Ein Agenten-, Chat- oder Bot-Lauf erreicht einen Endstatus. Blockierend, wenn ein Agent normal fertig wird. |
| `SubagentStop` | `{ commandKey, runStatus, status?, sessionId? }` | Ein Unteragent ist dabei, fertig zu werden. Blockierend. Unteragenten lösen `Stop` nicht aus. |

Ältere Enconvo-Namen wie `run_status_changed` und `agent_tool_step_changed` funktionieren weiterhin, sodass bestehende Hook-Dateien nicht sofort migriert werden müssen.

## Rezepte

### macOS-Benachrichtigung, wenn ein Agent fehlschlägt

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "STATUS=$(cat | jq -r '.params.runStatus // .params.status') && [ \"$STATUS\" = \"failed\" ] && osascript -e 'display notification \"An agent failed\" with title \"EnConvo\"'"
          }
        ]
      }
    ]
  }
}
```

### Statusänderungen von Agenten protokollieren

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "jq -c '{time: (.timestamp / 1000 | strftime(\"%Y-%m-%d %H:%M:%S\")), agent: .params.commandKey, status: (.params.runStatus // .params.status)}' >> ~/.enconvo/agent-status.log"
          }
        ]
      }
    ]
  }
}
```

### Tool-Aufrufe von Agenten protokollieren

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.params | \"\\(.status) \\(.toolName) \\(.toolCallId)\"' >> ~/.enconvo/agent-tools.log"
          }
        ]
      }
    ]
  }
}
```

### An Slack senden

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "http",
            "url": "https://hooks.slack.com/services/YOUR/WEBHOOK/URL"
          }
        ]
      }
    ]
  }
}
```

### Eigenes Skript

Erstelle ein Skript, das die Ereignisdaten von stdin liest:

```bash
#!/bin/bash
# ~/.enconvo/hooks/on-status-change.sh
INPUT=$(cat)
STATUS=$(echo "$INPUT" | jq -r '.params.runStatus // .params.status')
AGENT=$(echo "$INPUT" | jq -r '.params.commandKey')

echo "[$(date)] $AGENT -> $STATUS" >> /tmp/enconvo-hooks.log

if [ "$STATUS" = "failed" ]; then
  osascript -e "display notification \"$AGENT failed\" with title \"EnConvo\""
fi
```

Verweise in `~/.enconvo/hooks.json` darauf:

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "bash ~/.enconvo/hooks/on-status-change.sh"
          }
        ]
      }
    ]
  }
}
```

Mache das Skript ausführbar:

```bash
chmod +x ~/.enconvo/hooks/on-status-change.sh
```

## Fehlerbehebung

| Problem | Was zu tun ist |
| --- | --- |
| Ein Hook wurde nicht ausgeführt | Prüfe, ob `~/.enconvo/hooks.json` gültiges JSON ist, ob der Schlüssel der obersten Ebene zum Ereignisnamen passt und ob der Befehl funktioniert, wenn du ihn selbst ausführst. Hast du noch `~/.config/enconvo/hooks.json`, wird sie ignoriert, solange die neue Datei existiert. |
| Du bist nicht sicher, ob Hooks Enconvo blockieren | Nur `PreToolUse`, `Stop` und `SubagentStop` blockieren, und zwar bei Agentenläufen. Jeder andere Hook ist Fire-and-forget. Schlägt ein Hook fehl oder überschreitet das Zeitlimit, protokolliert Enconvo den Fehler und macht weiter, als gäbe es den Hook nicht. |
| Die Hooks eines Plugins laufen nicht | Öffne das Plugin und klicke auf **Hooks erlauben**. Nach einem Update, das sie geändert hat, prüfe sie und erlaube sie erneut. |
| Ein Befehl findet ein Skript oder Programm nicht | Verwende absolute Pfade. Die Auflösung von `~` in der Shell funktioniert, wenn der Befehl über eine Shell läuft, aber absolute Pfade lassen sich leichter debuggen. |

### Ein Skript von Hand testen

Leite eine Beispiel-Payload in das Skript:

```bash
echo '{"event":"Stop","params":{"commandKey":"agent|main","runStatus":"failed"},"timestamp":1742313600000}' | bash ~/.enconvo/hooks/on-status-change.sh
```
