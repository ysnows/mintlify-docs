스킬은 Enconvo가 워크플로를 안정적으로 따를 수 있도록 지침, 리소스, 선택적 스크립트를 하나로 묶어 둔 패키지입니다. 코드 리뷰 방법이나 회의록 정리 형식처럼 같은 절차를 반복해서 설명하고 있을 때 스킬로 만들어 두세요. 만든 스킬은 팀이나 커뮤니티와 공유할 수도 있습니다.

<Note>
스킬은 컨텍스트를 효율적으로 관리하기 위해 **점진적 공개(progressive disclosure)** 방식을 사용합니다. Enconvo는 먼저 각 스킬의 메타데이터(이름, 설명, 파일 경로)만 읽고, 스킬이 활성화될 때만 전체 지침을 불러옵니다.
</Note>

이 동영상은 스킬에 이어 MCP 서버, 플러그인, 확장 프로그램 스토어를 차례로 다룹니다.

## 스킬 관리하기

**설정 → 스킬**을 엽니다. 모든 에이전트가 이 스킬들을 공유하며, 각 에이전트 설정에서 자체 스킬을 추가할 수도 있습니다.

- 상단 카드에는 **모든 스킬**, **켜짐, 사용 안 함**, **여러 폴더에 있음**, **꺼짐** 개수가 표시됩니다. 카드를 클릭하면 해당 목록만 걸러 볼 수 있습니다.
- 각 행에는 **위치**(기본 제공 또는 출처 폴더·앱)와 **마지막 사용** 시점이 표시됩니다. 행 끝의 스위치로 에이전트가 필요로 하지 않는 스킬을 끄거나, 여러 개를 선택해 한꺼번에 끌 수 있습니다.
- **GitHub에서 추가**는 리포지토리에서 스킬을 설치하고, **가져오기**는 Mac의 폴더에서 스킬을 추가합니다. [스킬 설치하기](#스킬-설치하기)를 참고하세요.
- **내 스킬**에는 사용자가 만든 스킬이 출처(**녹음됨**, **학습함**, **스크립트**, **작성**, **설치됨**)별로 나열됩니다. 항목을 클릭하면 **단계**, **주의할 점**, **기록**을 볼 수 있습니다. [단계가 저장된 스킬](#단계가-저장된-스킬)을 참고하세요.

채팅 창에서는 왼쪽 아이콘 레일의 **플러그인**에서 스킬을 바로 열 수도 있습니다.

## 스킬의 구조

스킬은 `SKILL.md` 파일과 선택적인 스크립트·참고 자료가 들어 있는 폴더입니다.

```
my-skill/
├── SKILL.md          # Required: instructions + metadata
├── scripts/          # Optional: executable code
├── references/       # Optional: documentation
└── assets/           # Optional: templates, resources
```

### SKILL.md 형식

`SKILL.md`는 `name`과 `description`이 포함된 frontmatter 블록으로 시작해야 합니다.

```markdown
---
name: my-skill
description: Explain exactly when this skill should and should not trigger.
---

Step-by-step instructions for EnConvo to follow.
```

<Tip>
Enconvo는 `description`을 보고 스킬을 고르므로 적용 범위와 경계를 명확히 적으세요. 스킬을 **언제** 써야 하는지와 **언제 쓰지 말아야** 하는지를 함께 적는 것이 좋습니다.
</Tip>

## 스킬 사용하기

스킬을 이름으로 직접 부르거나, Enconvo가 요청에 맞는 스킬을 고르게 할 수 있습니다.

### 이름으로 스킬 부르기

SmartBar나 채팅에서 `/` 뒤에 스킬 이름을 입력합니다.

```
/code-reviewer Review this function for security issues
/meeting-notes Format these raw notes into a structured summary
/api-checker Check the health of api.example.com
```

원하는 스킬을 정확하게 불러오는 가장 확실한 방법입니다. 스킬만 목록으로 보려면 `$`를 입력하세요.

설치한 플러그인에 포함된 스킬도 `/` 및 `$` 메뉴에 나타나며, Claude Code와 같이 `plugin:skill` 형식으로 이름이 붙습니다.

### Enconvo가 자동으로 고르게 하기

스킬 이름을 지정하지 않으면 Enconvo가 `description`을 기준으로 요청과 가장 관련 높은 스킬을 연결합니다.

1. 입력: "Summarize these meeting notes into action items"
2. Enconvo가 사용 가능한 모든 스킬의 설명을 살펴봅니다
3. `meeting-notes` 스킬이 일치합니다("...format raw meeting transcripts into structured notes with action items...")
4. 해당 스킬이 활성화되고 지침에 따라 응답이 작성됩니다

단순히 같은 단어가 있는지가 아니라 의미를 기준으로 연결하므로 설명과 표현이 다르거나 다른 언어로 작성된 요청도 알맞은 스킬을 찾아냅니다. 에이전트가 특정 스킬을 항상 볼 수 있게 하려면 에이전트 설정의 **도구 및 스킬**에서 고정하세요. [에이전트](/ko/ai/agents)를 참고하세요.

### 잘 매칭되는 설명 작성하기

정확한 매칭은 잘 작성된 `description`에 달려 있습니다.

| 품질 | 예시 |
|---------|---------|
| **너무 모호함** | "Helps with code" |
| **너무 포괄적임** | "Does anything related to programming" |
| **좋음** | "Review code for bugs, security issues, and best practices. Use when the user asks for a code review or wants to improve code quality. Do not use for code generation or writing new code." |

좋은 설명에는 세 가지 요소가 들어갑니다.

- **하는 일**: "Review code for bugs, security issues, and best practices"
- **실행 시점**: "Use when the user asks for a code review"
- **제외 조건**: "Do not use for code generation or writing new code"

## 스킬 저장 위치

Enconvo는 범위가 서로 다른 여러 위치에서 스킬을 읽습니다.

| 범위 | 위치 | 용도 |
|-------|----------|------------|
| **프로젝트** | `$PROJECT/.agents/skills/` (`.enconvo/skills/`, `.claude/skills/`, `.codex/skills/` 포함) | 특정 프로젝트 또는 워크스페이스용 스킬 |
| **사용자** | `~/.agents/skills/` (`~/.enconvo/skills/`, `~/.claude/skills/`, `~/.codex/skills/` 포함) | 모든 프로젝트에서 쓰는 개인 스킬 |
| **시스템** | Enconvo에 기본 포함 | 누구나 쓸 수 있는 기본 제공 스킬 |

각 에이전트도 자체 스킬을 가질 수 있습니다. 에이전트 설정의 **스킬** 아래에서 추가하세요.

서로 다른 위치에 있는 두 스킬의 이름이 같아도 Enconvo는 하나로 합치지 않고 둘 다 유지합니다. **설정 → 스킬**에서는 이런 스킬을 **여러 폴더에 있음**에 표시합니다.

### 프로젝트 스킬

프로젝트 스킬은 프로젝트 폴더 안에 저장되며 해당 프로젝트가 활성 상태일 때만 사용할 수 있습니다.

```
my-project/
├── .agents/
│   └── skills/
│       ├── deploy-checklist/
│       │   └── SKILL.md
│       └── pr-template/
│           └── SKILL.md
├── src/
└── package.json
```

프로젝트의 규칙, 파일 구조, 도구에 맞춘 스킬에 사용하세요.

### 사용자 스킬

`~/.agents/skills/`에 있는 사용자 스킬은 모든 프로젝트에서 사용할 수 있습니다. 특정 프로젝트에 속하지 않는 개인 스킬에 사용하세요.

```
~/.agents/skills/
├── email-composer/
│   └── SKILL.md
├── meeting-notes/
│   └── SKILL.md
└── code-reviewer/
    └── SKILL.md
```

## 스킬 만들기

### 스킬 생성기로 만들기

가장 빠른 방법은 기본 제공 생성기를 실행하는 것입니다.

```
/skill-creator
```

생성기가 다음 단계를 안내합니다.

1. 스킬이 하는 일
2. 스킬이 실행되어야 하는 시점
3. 지침만 포함할지 스크립트도 포함할지 여부

지침만 포함하는 방식이 기본값이자 권장 방식입니다. 확정적인 동작이나 외부 도구가 필요할 때만 스크립트를 추가하세요.

### 직접 만들기

`SKILL.md` 파일이 들어 있는 폴더를 만듭니다.

<Steps>
  <Step title="스킬 디렉터리 만들기">
    ```bash
    mkdir -p ~/.agents/skills/my-skill
    ```
  </Step>
  <Step title="SKILL.md 작성하기">
    ```bash
    cat > ~/.agents/skills/my-skill/SKILL.md << 'EOF'
    ---
    name: my-skill
    description: Summarize selected text into bullet points. Use when the user asks for a summary or key takeaways. Do not use for translation or rewriting tasks.
    ---

    ## Instructions

    1. Read the selected text from the user's input.
    2. Identify the 3-5 most important points.
    3. Return a bullet-point summary.
    4. Keep each bullet under 20 words.
    EOF
    ```
  </Step>
  <Step title="목록에 표시되는지 확인하기">
    Enconvo는 스킬 변경 사항을 자동으로 감지합니다. 새 스킬이 보이지 않으면 Enconvo를 다시 시작하세요.
  </Step>
</Steps>

### 지침 작성하기

`SKILL.md`에서 frontmatter 아래 본문에는 AI가 따를 지침이 들어갑니다. 명확한 명령형 단계로 작성하세요.

````markdown
---
name: changelog-generator
description: Generate a changelog from git commits. Use when the user asks to create a changelog, release notes, or commit summary. Do not use for general git operations.
---

## Instructions

1. Read the git log for the specified date range or number of commits.
2. Group commits by category:
   - **Features**: New functionality (commits starting with "feat:")
   - **Fixes**: Bug fixes (commits starting with "fix:")
   - **Breaking Changes**: Changes that break backward compatibility
   - **Other**: Everything else
3. For each commit, write a user-facing description (not the raw commit message).
4. Format as markdown with version header, date, and categorized bullet points.
5. Highlight breaking changes with a warning callout.

## Output Format

```
## v1.2.0 (2024-01-15)

### Features
- Added dark mode support for all pages
- New export to PDF option in reports

### Fixes
- Fixed login timeout on slow connections
- Resolved duplicate notification issue

### Breaking Changes
⚠️ API endpoint `/v1/users` now requires authentication
```
````

### 좋은 스킬 작성 팁

- **한 스킬에 한 가지 목적만 담으세요.** 스킬 하나가 한 가지 일을 합니다. 너무 많은 일을 맡기면 올바르게 발동하기도, 유지 관리하기도 어렵습니다. 여러 작업을 아우르는 10단계 이상의 글이 된다면 별도 스킬로 나누세요.
- **입력을 구체적으로 밝히세요.** "선택한 텍스트를 읽는다", "첨부 파일을 파싱한다", "사용자 메시지의 URL을 사용한다"처럼 입력이 어디에서 오는지 정확히 적으세요.
- **출력 형식을 정의하세요.** 결과가 일관되도록 출력 형태를 구체적인 예시로 넣어 두세요.
- **예외 상황을 다루세요.** "커밋이 없으면 해당 범위가 비어 있다고 보고한다"거나 "입력이 올바른 JSON이 아니면 형식을 확인해 달라고 요청한다" 같은 흔한 예외 지침을 추가하세요.
- **명령형 단계로 쓰세요.** 입력, 절차, 기대 결과를 분명하게 적으세요. 모호한 지침은 들쑥날쑥한 결과를 만듭니다.
- **스크립트보다 지침을 우선하세요.** 일반 언어 지침이 작성·디버깅·수정이 더 쉽습니다. 확정적 동작이나 외부 도구가 필요할 때만 스크립트를 쓰세요.
- **명확한 경계를 두세요.** `description`에 스킬이 처리해야 할 일과 처리하지 말아야 할 일을 함께 밝히세요.
- **트리거 설명을 테스트하세요.** 여러 프롬프트를 시험해 스킬이 필요할 때 켜지고 필요 없을 때 켜지지 않는지 확인하세요.
- **스킬을 버전 관리하세요.** 팀과 공유하는 스킬은 git 같은 버전 관리에 두어 변경 내역을 추적하고 되돌리며 협업하세요.

## 스크립트 추가하기

실행 가능한 로직이 필요한 스킬에는 `scripts/` 폴더를 추가하세요.

```
my-skill/
├── SKILL.md
└── scripts/
    └── fetch_data.sh
```

`SKILL.md` 안에서 스크립트를 참조합니다.

````markdown
---
name: api-checker
description: Check API endpoint health and response times.
---

## Instructions

1. Run the health check script:
   ```bash
   bash scripts/fetch_data.sh $URL
   ```
2. Parse the JSON output.
3. Report status, response time, and any errors.
````

### 스크립트를 써야 할 때

| 스크립트를 사용할 때 | 지침만 사용할 때 |
|-----------------|---------------------------|
| 정확한 형식이나 계산처럼 확정적 출력이 필요할 때 | 주로 추론과 언어 처리로 해결되는 작업일 때 |
| 외부 API나 데이터베이스와 통신할 때 | AI의 기본 기능만으로 충분한 작업일 때 |
| 데이터를 프로그래밍 방식으로 가공·변환해야 할 때 | 글쓰기, 요약, 분석에 관한 작업일 때 |
| 인증이나 자격 증명 처리가 필요할 때 | 지침만으로 충분할 때 |

## 참고 자료 추가하기

스킬이 참조할 문서나 컨텍스트 파일을 함께 넣을 수 있습니다.

```
my-skill/
├── SKILL.md
├── references/
│   ├── api-docs.md
│   └── examples.md
└── scripts/
    └── run.sh
```

지침에서 해당 파일을 가리키도록 적습니다.

```markdown
Consult `references/api-docs.md` for the API schema before making requests.
```

참고 자료는 다음과 같은 경우에 유용합니다.

- 스킬이 따라야 하는 API 문서
- 스타일 가이드 또는 브랜드 가이드라인
- 코드 예시와 템플릿
- 특정 도메인 지식

## 스킬 설치하기

`/skill-installer`를 사용하면 Enconvo 스킬 스토어나 GitHub에서 스킬을 설치할 수 있습니다. Skills.sh, ClawHub, 직접 ZIP URL을 통한 설치도 지원합니다.

### Enconvo 스킬 스토어에서 설치

이름으로 스킬을 검색해 설치합니다.

```
/skill-installer pdf
```

Enconvo 스킬 스토어를 검색해 일치하는 스킬을 설치하며, 새로 설치된 스킬을 자동으로 감지합니다.

### GitHub에서 설치

GitHub 리포지토리 URL에서 바로 스킬을 설치합니다.

```
/skill-installer https://github.com/anthropics/skills/tree/main/skills/pptx
```

URL이 하위 폴더를 가리켜도 되므로 큰 리포지토리 전체를 복제하지 않고 스킬 하나만 설치할 수 있습니다.

### Mac의 폴더에서 설치

1. **설정 → 스킬**을 열고 **가져오기**를 클릭합니다.
2. 각각 `SKILL.md`가 들어 있는 스킬 하위 폴더들을 담은 폴더를 선택합니다.

Enconvo가 해당 폴더를 스킬 검색 경로에 추가하며, 포함된 스킬은 모든 에이전트가 공유합니다. 폴더 사용을 중단하려면 출처 메뉴에서 해당 폴더를 선택한 뒤 **폴더 제거**를 클릭하세요. 디스크에 있는 폴더 자체는 삭제되지 않습니다.

## 단계가 저장된 스킬

저장된 모든 워크플로는 자체 `SKILL.md`를 가진 스킬이기도 하며, 스킬은 이전에 수행했던 작업의 단계를 저장해 둘 수 있습니다. 이런 스킬을 실행하면 메인 모델을 거치지 않고 저장된 단계를 먼저 실행하므로 더 빠르고 저렴합니다. 버튼 위치가 바뀌는 등 맞지 않게 된 단계는 스킬 자체의 메모와 스크린샷을 참고해 복구하며, 그마저 실패할 때만 에이전트가 `SKILL.md`를 보고 작업을 수행합니다.

**내 스킬**에서 **저장된 단계를 먼저 실행**으로 표시된 스킬은 단계가 있는 스킬이고, **설명만**으로 표시된 스킬은 단계가 없는 스킬입니다. 각 스킬의 **기록**에서 실행 결과와 학습한 내용을 보고 이전 버전으로 복원할 수도 있습니다.

### 녹화를 스킬로 바꾸기

직접 수행한 작업의 녹화를 스킬로 변환할 수 있습니다. 녹화된 각 동작이 검증된 단계가 되며 복구용 스크린샷도 함께 저장됩니다. 한 번 실행에 성공할 때까지는 **초안** 상태로 유지됩니다.

### 스크립트를 단계로 실행하기

스킬은 자체 `scripts` 폴더에 [코드 모드](/ko/configuration/code-mode) 스크립트를 보관하고 한 단계로 실행할 수 있어, 도구 호출이 많은 작업도 단일 단계로 처리됩니다.

## 스킬이 작업 방식을 학습하게 하기

메모리가 사실을 학습하듯 스킬도 사용자가 선호하는 작업 방식을 학습할 수 있습니다. **설정 → 메모리**를 열고 **방법 학습**을 켜세요.

- 작업 방식을 바로잡아 주거나 단계가 복구되어야 했을 때 스킬이 즉시 학습합니다. 채팅에는 **실행 취소** 버튼이 달린 **학습함** 안내가 표시됩니다.
- 같은 작업이 두 번째로 등장하면 새 스킬로 만들어집니다.
- 메모리 검토와 메모리 정리 기능도 스킬을 함께 관리합니다.

**단계를 바꿀 때** 아래에서 **바로 사용** 또는 **먼저 묻기**를 고르면 스킬 단계 변경 시 바로 쓸지 안내의 **적용**을 클릭할 때까지 기다릴지 정할 수 있습니다. 주의할 점(Gotchas)은 어느 쪽을 고르든 바로 추가됩니다. 결제, 전송, 삭제 동작은 항상 먼저 확인을 거치며 키와 비밀번호는 절대 학습하지 않습니다.

## 스킬 관리하기

### 스킬 보기

**설정 → 스킬**에는 모든 에이전트가 공유하는 스킬이 표시됩니다. 상단에서 보기를 선택하세요.

| 보기 | 표시 대상 |
| --- | --- |
| **모든 스킬** | 여러 폴더에 사본이 있어도 모든 스킬을 한 번씩 표시 |
| **켜짐, 사용 안 함** | 매 채팅에서 에이전트에게 제공되지만 아직 쓰이지 않은 스킬 |
| **여러 폴더에 있음** | Claude Code와 Codex용 등 여러 폴더에 사본이 있는 스킬 |
| **꺼짐** | 에이전트에게 제공되지 않는 스킬 |

검색하거나 출처(**모든 출처**, **기본 제공**, **플러그인에서** 또는 특정 폴더)로 필터링하고, **이름 A~Z** 또는 **마지막 사용** 순으로 정렬할 수 있습니다.

### 스킬 업데이트하기

- **스토어 스킬**: `/skill-installer`를 다시 실행해 새 버전을 확인합니다.
- **GitHub 스킬**: 같은 URL로 설치 도구를 다시 실행합니다.
- **직접 만든 스킬**: `SKILL.md` 파일을 직접 수정하면 Enconvo가 변경 사항을 자동으로 감지합니다.

### 스킬 끄기

삭제하지 않고도 스킬을 끌 수 있습니다.

1. **설정 → 스킬**을 엽니다.
2. 해당 스킬을 찾습니다.
3. 스위치를 끕니다.

꺼진 스킬은 다시 켤 때까지 이름 호출이나 자동 매칭으로 에이전트가 사용할 수 없습니다. 다만 해당 스킬을 고정해 둔 앱 프로필에서는 계속 사용할 수 있습니다.

## 스킬 예시

### 코드 리뷰어

```markdown
---
name: code-reviewer
description: Review code for bugs, security issues, and best practices. Use when the user asks for a code review or wants to improve code quality. Do not use for code generation or writing new code.
---

## Instructions

1. Read the provided code carefully.
2. Check for:
   - Logic errors and edge cases
   - Security vulnerabilities (injection, XSS, etc.)
   - Performance issues
   - Code style and readability
3. Provide feedback as a numbered list.
4. For each issue, include:
   - Severity (Critical / Warning / Suggestion)
   - Line reference
   - Explanation and fix
```

### 회의록 정리

```markdown
---
name: meeting-notes
description: Format raw meeting transcripts into structured notes with action items. Use when the user provides meeting notes, transcripts, or asks to organize meeting content. Do not use for scheduling or calendar tasks.
---

## Instructions

1. Parse the meeting transcript or raw notes.
2. Extract and organize into sections:
   - **Attendees**: List all participants
   - **Key Decisions**: Bullet-point decisions made
   - **Discussion Summary**: 3-5 sentence overview
   - **Action Items**: Table with Owner, Task, Deadline
3. Use markdown formatting for readability.
```

### Git 커밋 메시지

````markdown
---
name: commit-message
description: Generate conventional commit messages from staged changes. Use when the user asks for a commit message or wants to commit changes. Do not use for general git operations like branching or merging.
---

## Instructions

1. Read the staged diff (use `git diff --staged`).
2. Identify the type of change:
   - feat: New feature
   - fix: Bug fix
   - docs: Documentation
   - refactor: Code restructuring
   - test: Adding tests
   - chore: Maintenance
3. Write a commit message following Conventional Commits format:
   ```
   type(scope): concise description

   - Detail 1
   - Detail 2
   ```
4. Keep the subject line under 72 characters.
5. Include a body only if the change needs explanation.
````

### API 문서 생성기

````markdown
---
name: api-docs
description: Generate API documentation from source code. Use when the user asks to document an API, endpoint, or function. Do not use for general code documentation or README files.
---

## Instructions

1. Read the source code file(s) provided.
2. For each endpoint or public function, document:
   - **Method & Path** (for HTTP) or **Signature** (for functions)
   - **Description**: What it does in one sentence
   - **Parameters**: Name, type, required/optional, description
   - **Response**: Structure and example
   - **Errors**: Possible error codes and meanings
3. Format as markdown with code examples.
4. Include a curl example for each HTTP endpoint.

## Output Format

### `POST /api/users`

Create a new user account.

**Parameters:**

| Name | Type | Required | Description |
|------|------|----------|-------------|
| email | string | Yes | User's email address |
| name | string | Yes | Display name |

**Response (201):**
```json
{ "id": "usr_123", "email": "user@example.com", "name": "John" }
```
````
