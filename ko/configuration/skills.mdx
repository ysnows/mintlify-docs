스킬은 지침, 리소스, 선택적 스크립트를 하나로 묶어 Enconvo가 워크플로를 안정적으로 따를 수 있게 해 줍니다. 코드 리뷰 방법이나 회의 노트 서식처럼 같은 절차를 계속 설명하고 있다면 스킬로 만드세요. 스킬은 팀이나 커뮤니티와 공유할 수 있습니다.

<Note>
스킬은 **점진적 공개**로 컨텍스트를 효율적으로 관리합니다. Enconvo는 각 스킬의 메타데이터(이름, 설명, 파일 경로)만 가지고 시작하고, 전체 지침은 스킬이 활성화될 때만 불러옵니다.
</Note>

이 영상은 스킬을 다루고, 이어서 MCP 서버, 플러그인, 확장 스토어를 다룹니다.

## 스킬 관리하기

**설정 → 스킬**을 여세요. 모든 에이전트가 이 스킬을 공유하며, 각 에이전트는 자체 설정에서 자기만의 스킬을 추가할 수 있습니다.

- 상단의 카드는 **모든 스킬**, **켜짐, 사용 안 함**, **여러 폴더에 있음**, **끔**의 개수를 보여줍니다. 카드를 클릭하면 해당 스킬만 나열됩니다.
- 각 행에는 **위치**(기본 제공이거나 출처가 되는 폴더 또는 앱)와 **마지막 사용** 시점이 표시됩니다. 에이전트에게 필요 없는 스킬은 행 끝의 스위치로 끄거나, 여러 개를 선택해 한꺼번에 끄세요.
- **GitHub에서 추가**는 저장소에서 스킬을 설치하고, **가져오기**는 Mac의 폴더에서 스킬을 추가합니다. [스킬 설치하기](#스킬-설치하기)를 참고하세요.
- **내 스킬**에는 내가 만든 스킬이 출처별로 나열됩니다. **녹음됨**, **학습함**, **스크립트**, **작성**, **설치됨**입니다. 하나를 클릭하면 **단계**, **주의할 점**, **기록**을 볼 수 있습니다. [저장된 단계가 있는 스킬](#저장된-단계가-있는-스킬)을 참고하세요.

채팅 창에서는 아이콘 레일의 **플러그인**에서 스킬을 창 안에서 바로 열 수도 있습니다.

## 스킬의 구성

스킬은 `SKILL.md` 파일이 있는 폴더이며, 선택적으로 스크립트와 참고 자료를 둘 수 있습니다.

```
my-skill/
├── SKILL.md          # Required: instructions + metadata
├── scripts/          # Optional: executable code
├── references/       # Optional: documentation
└── assets/           # Optional: templates, resources
```

### SKILL.md 형식

`SKILL.md`는 `name`과 `description`이 있는 프런트매터 블록으로 시작해야 합니다.

```markdown
---
name: my-skill
description: Explain exactly when this skill should and should not trigger.
---

Step-by-step instructions for EnConvo to follow.
```

<Tip>
Enconvo는 `description`으로 스킬을 고르므로 범위와 경계를 분명하게 적으세요. 스킬을 **언제** 사용하고 **언제** 사용하지 않는지 적어 두세요.
</Tip>

## 스킬 사용하기

스킬을 이름으로 호출하거나, 요청에 맞는 스킬을 Enconvo가 고르게 할 수 있습니다.

### 이름으로 스킬 호출하기

SmartBar나 채팅에서 `/` 뒤에 스킬 이름을 입력하세요.

```
/code-reviewer Review this function for security issues
/meeting-notes Format these raw notes into a structured summary
/api-checker Check the health of api.example.com
```

이 방법이 가장 확실합니다. 원하는 스킬이 정확히 사용됩니다. 스킬만 나열하려면 `$`를 입력하세요.

설치한 플러그인의 스킬도 `/`와 `$` 메뉴에 있으며, Claude Code처럼 `plugin:skill` 형식의 이름으로 표시됩니다.

### Enconvo가 고르게 하기

스킬을 지정하지 않으면 Enconvo가 `description`을 기준으로 요청과 가장 관련 있는 스킬을 찾아 연결합니다.

1. 이렇게 입력합니다: "이 회의 노트를 실행 항목으로 요약해 줘"
2. Enconvo가 사용 가능한 모든 스킬의 설명을 훑어봅니다
3. `meeting-notes` 스킬이 일치합니다("...format raw meeting transcripts into structured notes with action items...")
4. 스킬이 활성화되고 그 지침이 응답을 이끕니다

일치는 단순히 같은 키워드가 아니라 의미를 기준으로 하므로, 설명과 표현이 다르거나 다른 언어로 쓴 요청도 스킬을 찾습니다. 에이전트가 스킬을 항상 볼 수 있게 하려면 에이전트의 **도구 및 스킬** 설정에서 스킬을 고정하세요. [에이전트](/ko/ai/agents)를 참고하세요.

### 잘 일치하는 설명 쓰기

좋은 일치는 잘 쓴 `description`에 달려 있습니다.

| 품질 | 예시 |
|---------|---------|
| **너무 모호함** | "Helps with code" |
| **너무 광범위함** | "Does anything related to programming" |
| **좋음** | "Review code for bugs, security issues, and best practices. Use when the user asks for a code review or wants to improve code quality. Do not use for code generation or writing new code." |

좋은 설명에는 세 부분이 있습니다.

- **하는 일**: "Review code for bugs, security issues, and best practices"
- **사용할 시점**: "Use when the user asks for a code review"
- **사용하지 않을 시점**: "Do not use for code generation or writing new code"

## 스킬이 있는 곳

Enconvo는 여러 위치에서 스킬을 읽으며, 위치마다 적용 범위가 다릅니다.

| 범위 | 위치 | 용도 |
|-------|----------|------------|
| **프로젝트** | `$PROJECT/.agents/skills/` (`.enconvo/skills/`, `.claude/skills/`, `.codex/skills/`도 해당) | 하나의 프로젝트나 작업 공간을 위한 스킬 |
| **사용자** | `~/.agents/skills/` (`~/.enconvo/skills/`, `~/.claude/skills/`, `~/.codex/skills/`도 해당) | 모든 프로젝트에서 쓰는 개인 스킬 |
| **시스템** | Enconvo에 포함 | 누구나 쓸 수 있는 기본 제공 스킬 |

각 에이전트는 자체 스킬을 가질 수도 있습니다. 에이전트 설정의 **스킬**에서 추가하세요.

서로 다른 위치의 두 스킬이 같은 이름이면 둘 다 사용할 수 있으며 Enconvo가 합치지 않습니다. **설정 → 스킬**의 **여러 폴더에 있음**에 이러한 스킬이 나열됩니다.

### 프로젝트 스킬

프로젝트 스킬은 프로젝트 폴더 안에 있으며 해당 프로젝트가 활성화되어 있을 때만 사용할 수 있습니다.

```
my-project/
├── .agents/
│   └── skills/
│       ├── deploy-checklist/
│       │   └── SKILL.md
│       └── pr-template/
│           └── SKILL.md
├── src/
└── package.json
```

프로젝트의 규칙, 파일 구조, 도구에 의존하는 스킬에 사용하세요.

### 사용자 스킬

`~/.agents/skills/`의 사용자 스킬은 모든 프로젝트에서 사용할 수 있습니다. 하나의 프로젝트에 속하지 않는 개인 스킬에 사용하세요.

```
~/.agents/skills/
├── email-composer/
│   └── SKILL.md
├── meeting-notes/
│   └── SKILL.md
└── code-reviewer/
    └── SKILL.md
```

## 스킬 만들기

### 스킬 크리에이터로 만들기

스킬을 가장 빠르게 만드는 방법은 기본 제공 크리에이터입니다.

```
/skill-creator
```

크리에이터가 다음을 차례로 안내합니다.

1. 스킬이 하는 일
2. 스킬이 실행되어야 하는 시점
3. 지침만 둘지, 스크립트도 포함할지

지침만 두는 것이 기본값이자 권장 방식입니다. 결정적인 동작이나 외부 도구가 필요할 때만 스크립트를 추가하세요.

### 직접 만들기

`SKILL.md` 파일이 있는 폴더를 만드세요.

<Steps>
  <Step title="스킬 디렉터리 만들기">
    ```bash
    mkdir -p ~/.agents/skills/my-skill
    ```
  </Step>
  <Step title="SKILL.md 작성하기">
    ```bash
    cat > ~/.agents/skills/my-skill/SKILL.md << 'EOF'
    ---
    name: my-skill
    description: Summarize selected text into bullet points. Use when the user asks for a summary or key takeaways. Do not use for translation or rewriting tasks.
    ---

    ## Instructions

    1. Read the selected text from the user's input.
    2. Identify the 3-5 most important points.
    3. Return a bullet-point summary.
    4. Keep each bullet under 20 words.
    EOF
    ```
  </Step>
  <Step title="표시되는지 확인하기">
    Enconvo는 스킬 변경을 자동으로 감지합니다. 새 스킬이 나타나지 않으면 Enconvo를 다시 시작하세요.
  </Step>
</Steps>

### 지침 쓰기

프런트매터 아래의 `SKILL.md` 본문에는 AI가 따를 지침이 들어갑니다. 명확한 명령형 단계로 작성하세요.

````markdown
---
name: changelog-generator
description: Generate a changelog from git commits. Use when the user asks to create a changelog, release notes, or commit summary. Do not use for general git operations.
---

## Instructions

1. Read the git log for the specified date range or number of commits.
2. Group commits by category:
   - **Features**: New functionality (commits starting with "feat:")
   - **Fixes**: Bug fixes (commits starting with "fix:")
   - **Breaking Changes**: Changes that break backward compatibility
   - **Other**: Everything else
3. For each commit, write a user-facing description (not the raw commit message).
4. Format as markdown with version header, date, and categorized bullet points.
5. Highlight breaking changes with a warning callout.

## Output Format

```
## v1.2.0 (2024-01-15)

### Features
- Added dark mode support for all pages
- New export to PDF option in reports

### Fixes
- Fixed login timeout on slow connections
- Resolved duplicate notification issue

### Breaking Changes
⚠️ API endpoint `/v1/users` now requires authentication
```
````

### 좋은 스킬을 위한 팁

- **각 스킬을 한 가지에 집중시키세요.** 스킬 하나는 한 가지 일을 합니다. 너무 많은 일을 하는 스킬은 올바르게 실행시키기도 유지하기도 더 어렵습니다. 여러 작업을 다루는 단계가 10개 이상이라면 별도의 스킬로 나누세요.
- **입력을 구체적으로 적으세요.** 입력이 어디서 오는지 정확히 말하세요. "선택한 텍스트를 읽는다", "첨부 파일을 분석한다", "사용자 메시지의 URL을 사용한다"처럼요.
- **출력 형식을 정의하세요.** 결과가 일관되도록 출력이 어떤 모양이어야 하는지 구체적인 예시를 포함하세요.
- **예외 상황을 처리하세요.** 흔한 예외 상황에 대한 지침을 추가하세요. "커밋이 없으면 범위가 비어 있다고 알린다", "입력이 올바른 JSON이 아니면 형식을 확인해 달라고 요청한다"처럼요.
- **명령형 단계로 쓰세요.** 입력, 단계, 기대하는 출력을 분명히 적으세요. 모호한 지침은 결과가 들쭉날쭉해지는 원인이 됩니다.
- **스크립트보다 지침을 선호하세요.** 평범한 말로 쓴 지침이 쓰고, 디버그하고, 바꾸기 더 쉽습니다. 결정적인 동작이나 외부 도구가 필요할 때만 스크립트를 사용하세요.
- **명확한 경계를 사용하세요.** 설명에 스킬이 처리해야 할 것과 처리하지 말아야 할 것을 모두 적으세요.
- **실행 조건 설명을 테스트하세요.** 여러 프롬프트로 스킬이 실행되어야 할 때 실행되고 그렇지 않을 때 실행되지 않는지 확인하세요.
- **스킬의 버전을 관리하세요.** 팀이 공유하는 스킬은 버전 관리(git)에 두어 변경을 추적하고, 되돌리고, 협업할 수 있게 하세요.

## 스크립트 추가하기

실행 가능한 로직이 필요한 스킬에는 `scripts/` 폴더를 추가하세요.

```
my-skill/
├── SKILL.md
└── scripts/
    └── fetch_data.sh
```

`SKILL.md`에서 스크립트를 참조하세요.

````markdown
---
name: api-checker
description: Check API endpoint health and response times.
---

## Instructions

1. Run the health check script:
   ```bash
   bash scripts/fetch_data.sh $URL
   ```
2. Parse the JSON output.
3. Report status, response time, and any errors.
````

### 스크립트를 사용할 때

| 스크립트를 사용할 때 | 지침만 사용할 때 |
|-----------------|---------------------------|
| 결정적인 출력(정확한 형식, 계산)이 필요할 때 | 작업이 주로 추론과 언어에 관한 것일 때 |
| 외부 API나 데이터베이스와 상호작용할 때 | 작업이 AI의 기본 기능만 사용할 때 |
| 데이터를 프로그램으로 처리하거나 변환해야 할 때 | 작업이 글쓰기, 요약, 분석에 관한 것일 때 |
| 인증이나 자격 증명 처리가 필요할 때 | 지침만으로 충분할 때 |

## 참고 자료 추가하기

스킬이 참조할 수 있는 문서나 컨텍스트 파일을 포함하세요.

```
my-skill/
├── SKILL.md
├── references/
│   ├── api-docs.md
│   └── examples.md
└── scripts/
    └── run.sh
```

지침에서 이를 참조하세요.

```markdown
Consult `references/api-docs.md` for the API schema before making requests.
```

참고 자료는 다음과 같은 경우에 유용합니다.

- 스킬이 따라야 하는 API 문서
- 스타일 가이드나 브랜드 가이드라인
- 코드 예시와 템플릿
- 특정 분야의 지식

## 스킬 설치하기

`/skill-installer`로 Enconvo 스킬 스토어나 GitHub에서 스킬을 설치하세요. Skills.sh, ClawHub, ZIP 직접 URL에서도 설치할 수 있습니다.

### Enconvo 스킬 스토어에서

이름으로 스킬을 검색해 설치하세요.

```
/skill-installer pdf
```

Enconvo 스킬 스토어를 검색해 일치하는 스킬을 설치합니다. Enconvo는 새로 설치된 스킬을 자동으로 감지합니다.

### GitHub에서

GitHub 저장소 URL에서 바로 스킬을 설치하세요.

```
/skill-installer https://github.com/anthropics/skills/tree/main/skills/pptx
```

URL은 하위 폴더를 가리킬 수 있으므로, 큰 저장소 전체를 복제하지 않고 스킬 하나만 설치할 수 있습니다.

### Mac의 폴더에서

1. **설정 → 스킬**을 열고 **가져오기**를 클릭하세요.
2. 각각 `SKILL.md`가 있는 스킬 하위 폴더를 담은 폴더를 선택하세요.

Enconvo가 그 폴더를 스킬을 읽는 위치에 추가하며, 폴더의 스킬은 모든 에이전트가 공유합니다. 폴더 사용을 중단하려면 소스 메뉴에서 해당 폴더를 선택한 다음 **폴더 제거**를 선택하세요. 폴더 자체는 디스크에 그대로 남습니다.

## 저장된 단계가 있는 스킬

저장된 모든 워크플로는 자체 `SKILL.md`가 있는 스킬이기도 하며, 스킬은 이전에 수행한 작업의 단계를 보관할 수 있습니다. 이런 스킬을 실행하면 저장된 단계가 메인 모델 없이 먼저 실행되어 더 빠르고 저렴합니다. 버튼이 옮겨진 것처럼 더는 맞지 않는 단계는 스킬 자체의 노트와 스크린샷으로 복구됩니다. 그래도 실패할 때만 에이전트가 `SKILL.md`를 보고 작업을 수행합니다.

**내 스킬**에서 **저장된 단계를 먼저 실행**으로 표시된 스킬은 단계가 있는 스킬이고, **설명만**으로 표시된 스킬은 단계가 없는 스킬입니다. 각 스킬의 **기록**에는 실행 결과와 학습한 내용이 표시되며, 이전 버전으로 복원할 수 있습니다.

### 녹음을 스킬로 바꾸기

직접 수행한 작업의 녹음을 스킬로 바꿀 수 있습니다. 녹음된 각 동작은 검증된 단계가 되고, 스크린샷은 복구를 위해 보관됩니다. 스킬은 한 번의 실행이 성공할 때까지 **초안 작성** 상태로 남습니다.

### 스크립트를 단계로 실행하기

스킬은 [코드 모드](/ko/configuration/code-mode) 스크립트를 자체 `scripts` 폴더에 두고 단계 중 하나로 실행할 수 있으므로, 많은 도구 호출을 하는 작업이 하나의 단계로 실행됩니다.

## 스킬이 내 작업 방식을 학습하게 하기

메모리가 사실을 학습하듯이 스킬도 내가 작업을 선호하는 방식을 학습할 수 있습니다. **설정 → 메모리**를 열고 **방법 학습**을 켜세요.

- 작업 수행 방식을 바로잡거나 단계를 복구해야 했을 때 스킬이 바로 학습합니다. 채팅에 **실행 취소**가 있는 **학습함** 노트가 표시됩니다.
- 같은 작업이 두 번째로 나오면 새 스킬이 됩니다.
- 메모리 검토와 메모리 정리가 스킬도 관리합니다.

**단계를 바꿀 때**에서 **바로 사용**을 선택하거나, **먼저 묻기**를 선택해 스킬의 단계 변경이 노트의 **적용**을 클릭할 때까지 기다리게 할 수 있습니다. 주의할 점은 어느 쪽이든 바로 반영됩니다. 결제, 전송, 삭제는 항상 먼저 묻고, 키와 비밀번호는 절대 학습하지 않습니다.

## 스킬 관리

### 스킬 보기

**설정 → 스킬**에는 모든 에이전트가 공유하는 스킬이 나열됩니다. 상단에서 보기를 선택하세요.

| 보기 | 표시되는 내용 |
| --- | --- |
| **모든 스킬** | 여러 폴더에 사본이 있어도 모든 스킬을 한 번씩 |
| **켜짐, 사용 안 함** | 모든 채팅에서 에이전트에게 제공되지만 아직 사용하지 않은 스킬 |
| **여러 폴더에 있음** | Claude Code와 Codex용처럼 둘 이상의 폴더에 사본이 있는 스킬 |
| **끔** | 에이전트가 받지 않는 스킬 |

검색하거나, 출처(**모든 출처**, **기본 제공**, **플러그인에서**, 또는 특정 폴더)로 필터링하거나, **이름 A~Z** 또는 **마지막 사용**으로 정렬하세요.

### 스킬 업데이트하기

- **스토어 스킬**: `/skill-installer`를 다시 실행해 최신 버전이 있는지 확인하세요.
- **GitHub 스킬**: 같은 URL로 설치 프로그램을 다시 실행하세요.
- **내가 만든 스킬**: `SKILL.md` 파일을 직접 편집하세요. Enconvo가 변경을 자동으로 감지합니다.

### 스킬 끄기

스킬을 삭제하지 않고 끌 수 있습니다.

1. **설정 → 스킬**을 여세요.
2. 스킬을 찾으세요.
3. 스위치를 끄세요.

꺼진 스킬은 다시 켤 때까지 에이전트가 이름으로도 일치로도 사용할 수 없습니다. 해당 스킬을 고정한 앱 프로필은 계속 사용할 수 있습니다.

## 예시 스킬

### 코드 리뷰어

```markdown
---
name: code-reviewer
description: Review code for bugs, security issues, and best practices. Use when the user asks for a code review or wants to improve code quality. Do not use for code generation or writing new code.
---

## Instructions

1. Read the provided code carefully.
2. Check for:
   - Logic errors and edge cases
   - Security vulnerabilities (injection, XSS, etc.)
   - Performance issues
   - Code style and readability
3. Provide feedback as a numbered list.
4. For each issue, include:
   - Severity (Critical / Warning / Suggestion)
   - Line reference
   - Explanation and fix
```

### 회의 노트

```markdown
---
name: meeting-notes
description: Format raw meeting transcripts into structured notes with action items. Use when the user provides meeting notes, transcripts, or asks to organize meeting content. Do not use for scheduling or calendar tasks.
---

## Instructions

1. Parse the meeting transcript or raw notes.
2. Extract and organize into sections:
   - **Attendees**: List all participants
   - **Key Decisions**: Bullet-point decisions made
   - **Discussion Summary**: 3-5 sentence overview
   - **Action Items**: Table with Owner, Task, Deadline
3. Use markdown formatting for readability.
```

### Git 커밋 메시지

````markdown
---
name: commit-message
description: Generate conventional commit messages from staged changes. Use when the user asks for a commit message or wants to commit changes. Do not use for general git operations like branching or merging.
---

## Instructions

1. Read the staged diff (use `git diff --staged`).
2. Identify the type of change:
   - feat: New feature
   - fix: Bug fix
   - docs: Documentation
   - refactor: Code restructuring
   - test: Adding tests
   - chore: Maintenance
3. Write a commit message following Conventional Commits format:
   ```
   type(scope): concise description

   - Detail 1
   - Detail 2
   ```
4. Keep the subject line under 72 characters.
5. Include a body only if the change needs explanation.
````

### API 문서 생성기

````markdown
---
name: api-docs
description: Generate API documentation from source code. Use when the user asks to document an API, endpoint, or function. Do not use for general code documentation or README files.
---

## Instructions

1. Read the source code file(s) provided.
2. For each endpoint or public function, document:
   - **Method & Path** (for HTTP) or **Signature** (for functions)
   - **Description**: What it does in one sentence
   - **Parameters**: Name, type, required/optional, description
   - **Response**: Structure and example
   - **Errors**: Possible error codes and meanings
3. Format as markdown with code examples.
4. Include a curl example for each HTTP endpoint.

## Output Format

### `POST /api/users`

Create a new user account.

**Parameters:**

| Name | Type | Required | Description |
|------|------|----------|-------------|
| email | string | Yes | User's email address |
| name | string | Yes | Display name |

**Response (201):**
```json
{ "id": "usr_123", "email": "user@example.com", "name": "John" }
```
````
